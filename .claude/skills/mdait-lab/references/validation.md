# 妥当性確認

`npm test` と `lab sweep` は**検証**である。仕様どおり作れたかを見る。
**妥当性確認**は別のことを見る。使う人にとって本当に良くなったか、である。

この2つは代わりにならない。実測では、単体テスト 1843 件が緑で `lab sweep` も FAIL=0 の状態から、
妥当性確認だけが拾った欠陥が5件出た。すべて「入口をひとつ塞いだつもりが、別の入口は開いたまま」
という形をしていた。テストは自分が想定した経路しか通らないので、この種は構造的に取れない。

## 何をするか

**使い手を演じるエージェントに、実際に製品を使わせる。** そして製品を直したあと、
**同じ使い手に、その人自身の不満を突き返して聞き直す。**

後半が肝である。前半だけなら探索テストで、これは既存の `probe` と目的が重なる。
「直したと言うなら、不満を言った本人が受け入れるか確かめる」という往復が入って初めて、
テストが届かない場所に手が届く。

```mermaid
flowchart LR
  A[使い手を演じて触る] --> B[不満の台帳]
  B --> C[直す]
  C --> D[同じ使い手へ台帳を返す]
  D --> E[解消 / 部分的 / 未解消]
  E -->|部分的が残る| C
```

物差しはアサーションではなく**使い手の不満**である。だから台帳は消さずに残し、次の周回でも使う。

## 使い手をどう決めるか

**製品が壊れたときに失うものが違う人**を並べる。役職や属性ではない。

失うものが違えば、同じ画面を見ても目に入るものが違う。原稿が消えることを恐れる人は削除の通知を読み、
費用を気にする人は確認ダイアログの件数を読む。どちらか一方だけでは、もう一方の欠陥は見えない。

人数は目的に従わせる。**失うものの種類が出尽くしたら止める。** 増やしても同じ欠陥が重複するだけで、
費用だけが増える。逆に「初めて触る人」と「毎日使う人」の2つしか無ければ、たいてい足りない。

決めるときの問いはこれだけでよい。

- この製品が黙って壊れたとき、**何を失う人がいるか**
- その人は**どの画面を最初に見るか**
- その人は**説明書を読むか**

3つ目が効く。読まない人は、書いてあるのに伝わっていない欠陥を踏む。

## 使い手に課す規律

**製品を直させない。** 観察と再現手順の確定だけをさせる。直す役を兼ねると、
使い手は「自分なら直せる」と思った瞬間に不満を言わなくなる。

**逸脱は単独の再現手順に落とさせる。** 手順・期待・実際の3つが揃っていないものは、次の周回で使えない。

**本物の欠陥と、実験装置の限界を分けさせる。** 偽の AI が JSON を返せないだけの現象を製品の欠陥として
持ち帰ると、直すものが無いのに時間だけ溶ける。

**作業場を使い手ごとに分ける。** 同じ作業場を共有すると互いの状態を壊し合い、
何が原因で何が結果か分からなくなる。この実験場では `MDAIT_LAB_DIR` で分ける。

## 聞き直しの作法

ここを外すと、ただの再テストになって「部分的」が出てこない。**実測では、拾えた5件すべてが
「部分的」から出た。** 「解消」と「未解消」の2値にした瞬間、この手法の価値は消える。

**その人自身の不満だけを渡す。** 他人の不満や一般的な観点を混ぜない。混ぜると、
自分の文脈で判定しなくなる。

**新しい課題を探させない。** 例外は「今回の変更で悪くなったと思えるもの」だけ。
禁じないと発散して、直したかどうかの判定が薄まる。

**3値で答えさせる。** 解消 / 部分的 / 未解消。判定と併せて、**取り繕わない一言**を必ず書かせる。
判定表だけでは「直ったが、まだ引っかかる」が出てこない。

**あえて直さなかったものも渡す。** 改善は期待せず、**悪化していないことだけ**を確認させる。
直した範囲の外で壊していないかは、ここでしか分からない。

## 費用と、それに見合う場面

使い手ひとりにつきエージェントを1つ起こす。`lab sweep` のような決定的スイープとは性質が違い、
実費がかかる。CI に載せるものではなく、手で叩くものとして扱う。

見合うのは次の場面である。

- 利用者に見える振る舞いを**広く**変えたあと
- **原稿や成果物が失われうる**経路に手を入れたあと
- テストは緑なのに「本当に良くなったのか」が言い切れないとき

逆に、内部だけの変更や、単体テストで期待を書き切れる修正には要らない。

## 落とし穴

**「退行なし」を額面どおり受け取らない。** 使い手が触っていない範囲の退行は、使い手には見えない。
`npm test` と `lab sweep` は別途通す。この手法はそれらの代わりではなく、隙間を埋めるものである。

**一度の結論で線を引かない。** ある直し方を試して失敗しても、それは**その一つのやり方**が失敗した
だけである。「この方向は無理」と書くと、次の周回でその筋が検討されなくなる。実際、この実験場でも
「推測に踏み込まない」と広く書いた判断が、後の対話で過度な一般化だったと分かった。
失敗を記録するときは、**何を試して何が起きたか**まで書く。

**使い手の指摘を鵜呑みにしない。** 手順が現実的でないことがある（この実験場では、原稿を丸ごと
書き直してマーカーごと消してしまった例があった）。判定の前に、自分で最小の再現を取り直す。
