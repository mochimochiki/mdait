# unit-state（外部ストア）の頑健性

> `markers.mode: "external"` で使う `.mdait/unit-state` について、**文書がふつうに編集・移動・削除されたときにどこまで状態が生き残るか**を実測し、embedded との差と、埋めるべき穴をまとめる。
>
> 実測スクリプト: `scripts/exploratory/probe-robustness.js`。VS Code を起動せずに sync/trans を直接動かし、同じ操作を embedded と external の両方で流して結果を並べる。
>
> ```bash
> npm run compile && node scripts/exploratory/probe-robustness.js
> ```
>
> テストワークスペース（`src/test/unit/workspace`）を書き換えるが終了時に自動復元する。オプションは [scripts/exploratory/README.md](../../scripts/exploratory/README.md) を参照。

---

## 1. いま何がどう保存されているか

| モード | 状態の置き場所 | 1つのユニットを指す「住所」 |
|---|---|---|
| embedded | 本文中の HTML コメント `<!-- mdait ... -->` | **本文そのもの**（コメントが文章と一緒に動く） |
| external | `.mdait/unit-state`（TSV 1ファイル） | **ファイルパス + 何番目か（order）** |

`unit-state` の1行は `path / order / level / titleHash / hash / from / need` の7列。読み書きは `UnitStateStore` に集約され、parse/stringify には `ExternalMarkerProvider` が橋渡しする。

- **読むとき**（`attachMarkers`）: そのファイルの行を order 順に並べ、**パースしたユニット配列の n 番目に n 番目の行を当てる**。`titleHash` は照合するが、食い違ってもログに出すだけで採用は index のまま。
- **書くとき**（`detachMarkers`）: ユニット配列の index をそのまま order として全行を上書きする。ユニットが減っても**末尾の余った行は消さない**。

この2点が、以下の壊れ方すべての出どころである。

## 2. 実測結果（embedded と external を同じ操作で比較）

原文4ユニット（導入＋第1〜3章）を翻訳完了状態にしてから、1操作だけ加えて `sync` した結果。

| # | 操作 | embedded | external | 差 |
|---|---|---|---|---|
| S1 | 原文の1章を編集 | 該当章だけ `revise` | 同じ | なし |
| S2 | 訳文を手で編集 | 保持・need なし | 同じ | なし |
| S3 | **原文の途中に章を挿入** | 新章だけ `translate`、他は無傷 | **対応が1つずつズレる**。第2章の訳が「第1.5章」に紐づき、全章 `revise`、訳文に第3章が二重に生える | **重大** |
| S4 | **原文の途中の章を削除** | 対応する訳だけ削除、他は無傷 | **残った訳が別の章に紐づく**。`unit-state` に余った行が残留 | **重大** |
| S5 | **原文の章を入れ替え** | 無傷（need も付かない） | **第2章の訳↔第3章の原文に交差**。両方 `revise` | **重大** |
| S6 | 原文だけリネーム | 旧訳文が孤立（状態は残る）／新パスは全 `translate` | 旧訳文が孤立し**状態も全消し**（マーカー無しの素のファイルになる） | external が弱い |
| S7 | 原文・訳文を揃えてリネーム | **完全に無傷** | 訳文本文は残るが**全ユニット `review`** | external が弱い |
| S8 | フォルダ移動（両方） | **完全に無傷** | 全ユニット `review` | external が弱い |
| S9 | 原文を削除 | 訳文は残り状態も残る | 訳文は残るが**状態は全消し** | external が弱い |
| S10 | 混合（挿入＋編集＋両方リネーム） | 挿入＝`translate`／編集＝`revise`／他は無傷 | **ズレ＋二重章＋全 `review`** | **重大** |
| S11 | `unit-state` を外部で削除 | （影響なし） | 対応は復元され全 `review` に倒れる | 想定どおり |
| S12 | 訳文が外部でマーカーごと差し替わって戻ってくる | **全 `translate`**（次の翻訳で人の訳が上書きされる） | 差し替えを新しい訳として受理、need なし | **external が強い** |
| S13 | S3 のあと `trans` まで実行 | 新章が正しい位置に訳出され他は無傷 | **訳文に第3章が二重に残り、第1.5章の訳は生まれない** | **重大** |
| S14 | 訳文ファイルを削除 | 原文から作り直し `translate` | 同じ | なし |

（S13 の `revise` が残るのは決定的モック AI の限界。二重章と新章の欠落は実 LLM でも起きる構造的な結果）

### 何が起きているか（S3 の内訳）

1. 原文に章が1つ増える → 原文のユニットは5つになる。
2. `attachMarkers` が「n 番目の行を n 番目のユニットへ」当てる → **挿入位置より後ろの原文ユニットが、1つ前のユニットのハッシュを名乗る**。
3. sync は `訳文の from == 原文の hash` で対応を取る。入力が既に汚れているので、対応付け自体は正しく動いたまま**間違ったペア**を作る。
4. 間違ったペアが `from` として `unit-state` に書き戻され、以後の正となる。

つまり**間違いが検知されずに保存され、次の翻訳で本文にまで及ぶ**。これが external で最も危険な性質である。

---

## 3. 診断: 壊れる原因は2つだけ

### 原因A: ユニットの住所が「何番目か」

挿入・削除・並べ替えは、文書編集でいちばん普通の操作なのに、そのたびに全ユニットの住所がズレる。embedded がこれに強いのは、住所が「本文のどこにコメントが書かれているか」で、文章と一緒に動くからである。

なお `unit-state` には既に **`hash`（そのユニット本文の CRC32）と `titleHash` と `level`** が入っている。**ズレを直すのに必要な情報は全部そろっていて、使っていないだけ**である。

### 原因B: ファイルの住所が「パス」で、しかも消す側に倒れている

- `sync` の最後で `cleanupOrphans(validTargetPaths)` が走り、**いまスキャンで見つかったパスに無い行を即削除する**。リネーム・移動・原文削除で状態が全消しになるのはこれ。
- 消える前に「同じ内容の行が別パスに移っただけでは？」を確かめる手順が無い。
- ファイル名変更を知る手段（`onDidRenameFiles`）を拡張機能がどこにも購読していない。
- スキャン結果に依存して消すので、設定ミス・sparse checkout・一時的なフォルダ退避でも**全行が消えうる**。

補足: 「ファイルが移動しても状態が迷子になる」問題は **embedded にもある**（S6 のとおり旧訳文が孤立し、進捗の分母だけが増える。誰にも通知されない）。external はそこに「状態も消える」が上乗せされている。

### 副次的な穴

- **余った行が残る**: ユニットが減っても末尾行が消えない（S4）。次に章が増えたとき、その古い行を拾う。`delete-unit.ts` だけが手動で末尾を刈っており、同じ手当てが sync 経路に無い。
- **列数が固定**: ローダーは7列ちょうどの行しか読まない。列を足す変更は、既存の `unit-state` を**警告なしで全行スキップ**する。形式を変えるならバージョン行と移行が要る。
- **union merge との相性**: `.gitattributes` の `merge=union` は、行が (path, order) キーだと**同じ order の行が2つ並ぶ**形で衝突を残す（後勝ちで潰れる）。内容キーで照合できれば被害が減る。

## 4. embedded との差（どちらが強いかは操作による）

| 観点 | embedded | external |
|---|---|---|
| 章の挿入・削除・並べ替え | **強い**（本文と一緒に動く） | 弱い（住所がズレる） |
| リネーム・フォルダ移動 | 中（状態は残るが対応は切れる） | 弱い（状態も消える） |
| 本文からコメントが失われる外部処理（整形ツール・翻訳ベンダー往復・コピペ） | 弱い（S12: 状態が消え、次の翻訳で人の訳を上書きしうる） | **強い**（本文に何も無くても状態は別ファイルに残る） |
| 見た目（画面にハッシュが出るか） | 出る | 出ない |
| 原文を書き換えるか | 書き換える（初回 sync で全件） | 書き換えない |
| git の衝突 | ファイル単位に分散 | 1ファイルに集中（union merge で緩和） |
| 章の複製（同じ章をコピペ） | ハッシュが重複し曖昧になる | 同上（住所は index なので別問題として発生） |

**要点**: embedded は「文書の中の変化」に強く「文書の外の処理」に弱い。external はその逆。external を既定にするなら、embedded が無料で持っている「文書の中の変化への追従」を、**内容による照合で作り直す**必要がある。

## 5. 埋め方（提案・段階順）

満たしたい性質:

- **P-a**: ユニットの同一性は「何番目か」ではなく**内容**（hash / titleHash / level）で決める。
- **P-b**: ファイルの同一性はパスを第一候補にしつつ、**移動を追える**ようにする。
- **P-c**: **走査の副作用で状態を消さない**。追えなかったものは削除ではなく「要対応」に倒す。
- **P-d**: 迷子になった対応は**画面に出る**し、人が再リンクできる。
- **P-e**: どんな壊れ方からも `sync` で再構築できる（現行の不変条件を維持）。

### 段階A: 本文の追従（原因A・最優先）

`ExternalMarkerProvider.attachMarkers` を index 当てから**並び合わせ（アライン）**に変える。手順は sync の `SectionMatcher` と同じ考え方:

1. 「保存済みの行の `hash`」と「いまパースしたユニットの本文ハッシュ」が一致するものを**錨（アンカー）**として先に確定する（順序は単調に保つ）。
2. 錨と錨の間の区間だけ、`titleHash` + `level` の一致で埋める。
3. それでも決まらない分は区間内の順序で埋め、余った行・余ったユニットは対応なしとする（＝ユニットはマーカー無し、行は破棄候補）。

`detachMarkers` は新しい並びで書き直し、**ユニット数を超える行を必ず刈る**（`UnitStateStore` に「このパスの行を丸ごと置き換える」API を置き、`delete-unit.ts` の手当ても畳む）。

これで S3 / S4 / S5 / S10 / S13 が embedded 同等になる。**外部ファイルの形式は変えない**（必要な列は既にある）。

### 段階B: ファイルの追従（原因B）

1. **VS Code 内のリネーム・移動**: `workspace.onDidRenameFiles` を購読し、`unit-state` の `path` を書き換える（フォルダ移動は前方一致で一括）。これで S7 / S8 が無傷になる。
2. **外で起きたリネーム**（`git mv`・ターミナル・別エディタ）: sync の掃除前に**内容による再リンク**を挟む。「行があるのに実体が無いパス」と「実体があるのに行が無いパス」を突き合わせ、ユニットのハッシュ集合が十分重なり、かつ**1対1に定まるときだけ**移送する。コピー（旧パスも残っている）は移送しない。
3. **掃除を消さない方向へ**: `cleanupOrphans` を即削除から「孤立として残す（または退避ファイルへ移す）」に変える。加えて**安全弁**として、1回の sync で孤立と判定された割合が閾値を超えたら削除も退避もせず報告だけにする（設定ミス・sparse checkout で全消しになるのを防ぐ）。

### 段階C: 見えるようにする（ux.md F-10 / UX-R5 段階4のゲート）

- sync 結果に `relinked` / `orphaned` を持たせ、完了通知と実行レポートに出す。
- ツリーに「原文と結びついていない訳文」を出し、行から**再リンク**（原文を選んで結び直す）と**破棄**を選べるようにする。
- これは embedded 側の F-10（分母だけ増えて誰も気づけない）も同時に塞ぐ。

### 段階D: frontmatter の外部化と external 既定化（ADR-260802-04）

A〜C の後に行う。`unit-state` に frontmatter マーカー用の枠を作る（例: `order = -1` の行。7列のままで表現できる）。

**注意すべき性質**: frontmatter まで外に出すと、external の Markdown は**mdait の痕跡を1文字も持たない**。つまり「リネームされたファイル」と「新しく作られたファイル」が本文以外では区別できなくなる。段階B の内容による再リンクは、そのとき**唯一の手がかり**になる。

代案として「frontmatter に `mdait: id:` を1行だけ残す」も考えられる（パスの同一性が完全に解決し、行数は1本）。ただし「原文を1文字も書き換えない」という ADR-260802-04 の主目的とは正面からぶつかるため、内容による再リンクが実用に足りないと分かった場合の退避案として置いておく。

## 6. 段階Aの検討メモ（実装前に決めておくこと）

- **同じ本文の章が複数あるとき**: 錨が曖昧になる。単調性を保った上で「元の order に近い方」を優先する。決められない組は錨にせず区間の順序埋めに委ねる。
- **原文側と訳文側で必要な錨が違う**: 原文行は `hash`（自分の本文）だけを持ち、訳文行は `hash`（訳文の本文）と `from`（原文のハッシュ）を持つ。どちらも「自分の本文ハッシュ」で錨を打てるので、同じアルゴリズムでよい。
- **手を入れた訳文**: 訳文の本文が変われば `hash` が合わなくなり錨にならない。`titleHash` + `level` と区間順序で拾う（embedded でも同じ精度）。
- **回帰の見張り**: `probe-robustness.js` を `npm run test:explore` の系列に組み込み、S1〜S14 の期待結果を固定する。「embedded と external の結果が一致すること」を判定条件にできるのが強い（S12 のように意図して違う項目だけ明示的に除外する）。

---

## 7. 現時点の結論

- external は **`markers.mode` を切り替えて使う分にはすでに動く**が、**章の挿入・削除・並べ替えに対して静かに壊れる**。しかも壊れた対応が保存され、次の翻訳で本文に及ぶ。これは「気づけない」種類の壊れ方で、いまの external の最大の弱点である。
- リネーム・移動・原文削除では**状態が消える**。ただし訳文の本文は消えないため、復旧は `review` からのやり直しで済む（S7/S8/S11）。危険度は挿入・削除より低い。
- 直すのに**外部ファイルの形式変更は要らない**。必要な情報（本文ハッシュ・タイトルハッシュ・レベル）は既に1行に入っている。
- 段階A（内容による並び合わせ）だけで、実測した重大ケースはすべて embedded 同等になる。段階B・C は ADR-260802-04 が保留の前提条件として挙げている「再リンクと孤立の可視化」そのものであり、embedded 側の欠陥（F-10）も同時に塞ぐ。
