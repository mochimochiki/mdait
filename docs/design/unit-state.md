# unit-state（外部ストア）の頑健性

> `markers.mode: "external"` で使う `.mdait/unit-state` について、**文書がふつうに編集・移動・削除されたときにどこまで状態が生き残るか**を実測し、embedded との差と、埋めるべき穴をまとめる。
>
> 実測スクリプト: `scripts/exploratory/probe-robustness.js`。VS Code を起動せずに sync/trans を直接動かし、同じ操作を embedded と external の両方で流して結果を並べる。
>
> ```bash
> npm run compile && node scripts/exploratory/probe-robustness.js
> ```
>
> テストワークスペース（`src/test/unit/workspace`）を書き換えるが終了時に自動復元する。オプションは [scripts/exploratory/README.md](../../scripts/exploratory/README.md) を参照。

## 1. いま何がどう保存されているか

| モード | 状態の置き場所 | 1つのユニットを指す「住所」 |
|---|---|---|
| embedded | 本文中の HTML コメント `<!-- mdait ... -->` | **本文そのもの**（コメントが文章と一緒に動く） |
| external | `.mdait/unit-state`（TSV 1ファイル） | **ファイルパス + 何番目か（order）** |

`unit-state` の1行は `path / order / level / titleHash / hash / from / need` の7列。読み書きは `UnitStateStore` に集約され、parse/stringify には `ExternalMarkerProvider` が橋渡しする。

- **読むとき**（`attachMarkers`）: 行といまのユニットを**内容で突き合わせる**（`unit-state-align.ts`。詳細は §10）。
  かつては「n 番目の行を n 番目のユニットに当てる」方式で、これが §2・§3 の壊れ方の原因だった。
- **書くとき**（`detachMarkers`）: ユニット配列の index をそのまま order として全行を上書きし、
  ユニットが減っていれば末尾の余った行を刈る（ユニットが 0 件のときは刈らない）。

なお `hash` 列に入るのは `unit.marker.hash`（＝前回 sync 時点のハッシュ）であって、いまの本文のハッシュではない。両者が一致するのは sync / trans が更新した直後だけである（後述の段階Aの前提に効く）。

| # | 操作 | embedded | external | 深刻度 |

| S21 | 章の統合（末尾の章を前の章に吸収） | 正しく3ユニット、統合先だけ `revise` | **embedded と完全に同一**（末尾操作なので index がズレない）。ただし余り行が残留 | 無傷 |

| S26 | 原文へ章挿入＋訳文の別章を人手編集 | 手編集の訳を保持・need なし。新章だけ `translate` | **人が直した訳が別の章に紐づけられ `revise`**（次の trans で上書きされる） | **誤対応** |
| S27 | 原文へ章挿入＋訳文の章を削除 | 消された訳は原文から復元し `translate`、他は無傷 | 誤対応＋訳文が5ユニットに膨らむ | **誤対応** |
| S28 | 章の入れ替え＋フォルダ移動 | **完全に無傷** | 全 `review`＋`from` が交差 | **誤対応**（ただし全 `review` で気づける） |
| S29 | 挿入→sync→別の章を削除→sync | 正しい | 1段目の重複章は消えるが**ズレは残ったまま固定**。余り行が残留 | **誤対応**（累積はしないが自己修復もしない） |
| S30 | 先頭ユニット（H1）を削除 | 正しく3ユニット、無傷 | 全ユニットがズレ、**第3章の訳が消滅**。原文に無い H1 が訳文の先頭に居座り文書構造も壊れる | **本文が壊れる** |
| S31 | 文書の先頭に H1 を挿入 | 新 H1 だけ `translate`、他は無傷 | 全4ユニットがズレて全 `revise`＋重複章 | **誤対応** |
| S32 | 壊れた状態で sync を3回 | 1回目と同一 | **1回目と同一**（増殖も振動もしない） | 無傷（＝壊れが冪等に固定される） |
| S33 | frontmatter 付き文書へ章を挿入 | frontmatter マーカーは無傷。本文は S3 と同じ | frontmatter マーカーは**embedded と同一で無傷**。本文だけ S3 と同じ壊れ方 | **誤対応**（frontmatter は無事） |
| S34 | frontmatter 編集＋章削除 | frontmatter に正しく `revise`。本文も正しい | frontmatter は正しい。本文は S4 と同じ | **本文が壊れる**（frontmatter は無事） |
| S35 | frontmatter 付き訳文を削除→sync で作り直し→trans | **frontmatter が永久に翻訳されない** | **embedded と完全に同一の壊れ方** | **両モード共通の重大欠陥**（§5参照） |

### 読み取れること

- **壊れ方は「訳文の末尾から N 個が消える」という規則性を持つ**。原文のユニットが N 個減ると、訳文の末尾 N 個が対応先を失い `autoDelete` で本文ごと消える（S4 / S25 / S30 / S34）。逆に増えたときは末尾に未翻訳の複製が生える。
- **末尾だけの操作は無傷**（S21）。ズレるのは「操作位置より後ろ」なので、先頭に近いほど被害が大きい（S30 / S31 は全ユニットに及ぶ）。
- **壊れは累積しない代わりに自己修復もしない**（S29 / S32）。sync を何回流しても同じ壊れた状態に落ち着く。直るのは原文を元に戻した場合だけで、しかもユニット数が変わらない操作に限る（S23）。
- **同一本文の章があると被害が最悪化する**（S25）。ズレた `from` が別位置の同一ハッシュに**たまたま一致してしまい**、対応表としては成立したまま中身が入れ替わる。
- **人手で直した訳ほど危ない**（S26）。手修正した訳文が別の章に紐づけられ、次の trans でその章の差分に合わせて上書きされる。

## 4. 診断: 壊れる原因は2つだけ

### 原因A: ユニットの住所が「何番目か」

挿入・削除・並べ替えは文書編集でいちばん普通の操作なのに、そのたびに操作位置より後ろの全ユニットの住所がズレる。embedded がこれに強いのは、住所が「本文のどこにコメントが書かれているか」で、文章と一緒に動くからである。

sync 自体は正しく動いている。`attachMarkers` が渡した入力が既に汚れているため、対応付け（訳文の `from` == 原文の `hash`）が**正しく動いたまま間違ったペア**を作り、それが `unit-state` に書き戻されて次の正になる。

### 原因B: ファイルの住所が「パス」で、しかも消す側に倒れている

- `sync` の最後で `cleanupOrphans(validTargetPaths)` が走り、**いまの走査で見つからなかったパスの行を即削除する**。
- 消える前に「同じ内容の行が別パスに移っただけでは？」を確かめる手順が無い。
- ファイル名変更を知る手段（`onDidRenameFiles`）をどこも購読していない。
- **さらに根本的な問題**: 原文と訳文のペアは `sourceDir` 相対パスを `targetDir` に貼って導出されるだけで、対応関係はどこにも永続化されていない。だから原文 `a.md` → `b.md` のリネームでは、
  1. 旧訳文 `en/a.md` は**ファイルも行も旧パスに残り続ける**（「行があるのに実体が無い」にも「実体があるのに行が無い」にも該当しない）
  2. 新パス `en/b.md` が無いので `syncNew` が走り、**原文を丸写しした未翻訳の複製訳文が生成される**

  これは実測 S6 が両モードで示したとおりで、**unit-state の行だけを追随させても訳は迷子のまま**である。

補足: 「ファイルが移動しても状態が迷子になる」問題は **embedded にもある**（`docs/ux.md` F-10）。external はそこに「状態も消える」が上乗せされている。

### 副次的な穴

- **余った行が残る**: ユニットが減っても末尾行が消えない。**訳文側だけでなく原文側にも残る**（S25 / S30 では ja 側に同一ハッシュの重複行ができる）。`delete-unit.ts` だけが手動で末尾を刈っており、同じ手当てが sync 経路に無い。
- **列数が固定**: ローダーは7列ちょうどの行しか読まない。列を足す変更は、既存の `unit-state` を**警告なしで全行スキップ**する。形式を変えるならバージョン行と移行が要る。
- **union merge との相性**: `.gitattributes` の `merge=union` は行を両方残すが、ローダーが `(path, order)` キーで後勝ちに潰すため、内容キーでの照合を入れても**潰れた後**を見ることになる。掃除を止めると旧パス行が恒久的に残る。

## 5. external とは無関係に見つかった欠陥

調査中に、**マーカーの保管方式とは関係なく壊れている**箇所が見つかった。これらは external 化の前提条件ではないが、別途手当てが要る。

### (1) 【重大】frontmatter の翻訳が、同じ内容に戻ると永久にスキップされる（両モード）

再現（VS Code の1セッション内）:
1. frontmatter 付きの原文を sync → 訳文ができる（`front: '... need:translate'`）
2. trans → frontmatter が翻訳される
3. **訳文ファイルを削除する**（やり直したいときの典型操作）
4. sync → 訳文が**バイト単位で手順1と同一の内容**で作り直される（ディスク上は `need:translate`）
5. trans → **frontmatter だけ翻訳されない。何度やっても変わらない**

原因（コードと最小再現で確認済み）:

- `FrontMatter.parse` は `matter(markdown)` の戻り値の `data` を**そのまま保持**する（`src/core/markdown/front-matter.ts:67`）
- gray-matter は**内容文字列をキーに parse 結果をキャッシュし、同じ内容には同じ `data` オブジェクト参照を返す**（`a.data === b.data` が `true` であることを実測で確認）
- mdait はその `data` を破壊的に書き換えるため、キャッシュの中身が「翻訳後」の状態に汚染される
- 内容が同一の文書を再パースすると `need:translate` の付いていない古いマーカーが返り、frontmatter の翻訳判定が素通りする

Extension Host は長時間動く1プロセスなので実運用で起きる。git checkout や取り消しで以前とまったく同じ内容に戻したときにも発火し、**VS Code を再起動するまで直らない**。本文だけ翻訳されるので「一部だけ訳されない」形になり、原因が非常に分かりにくい。

手当ての方向: `FrontMatter.parse` で受け取った `data` を保持する前に複製する（gray-matter のキャッシュ挙動に依存しない形にする）。

### (2) 差分ゼロの `revise` が残る（両モード）

原文の見出しレベルを下げて sync し、そのあと元に戻して sync すると、原文のハッシュは完全に元へ戻るのに訳文側は `from=X need:revise@X` になる（S23）。改訂すべき差分がゼロなのに要対応が残る。

### (3) 対象言語を絞って sync すると、選択外の言語の行が消える（external のみ・**実測で確認 → 修正済み**）

`sync` は選択中の pair だけを走査し、`validTargetPaths` もそこからしか作られない。`cleanupOrphans` は集合に無いパスを全削除するため、**ja→en だけ選んで sync すると fr の行が消える**。「走査対象外」と「実体が無い」を同じ概念で扱っているのが原因で、掃除を止める方向に変えると今度は選択外の全行が毎回「孤立」として上がってくる。

実測（S62 / S63）: 原文を1文字も触らず en だけ選んで sync するだけで、fr の行が全消えし、次の sync で fr が**全ユニット `need:review`** に倒れた。対応は §12。

### (4) キー正規化が2系統ある（external のみ・**コード上の帰結 → 修正済み**）

行のキーはワークスペースルート基準（`toWorkspaceRelativePath`）だが、`validTargetPaths` の**非MD分だけ** config ベースディレクトリ基準（`FileExplorer.normalizePath`）。カスタム config パスで両者がずれると、非MDの行が毎 sync 全滅する。対応は §12。

## 6. embedded との差（どちらが強いかは操作による）

| 観点 | embedded | external |
|---|---|---|
| 章の挿入・削除・並べ替え | **強い**（本文と一緒に動く） | 弱い（住所がズレ、訳文が消える） |
| 同一本文の章が複数ある文書 | **強い**（実測で正しく処理） | 弱い（最悪ケース。中身が入れ替わる） |
| 原文・訳文を揃えたリネーム／フォルダ移動 | **完全に無傷**（並べ替えと同時でも無傷） | **無傷**（§18。エディタ上の移動のみ） |
| 原文だけリネーム | **無傷**（§18。訳文を連れて動かす） | **無傷**（§18。同左。外での移動は段階4） |
| 原文削除 | 状態は残る | 状態は残る（§17。孤立として画面に出る） |
| 本文からコメントが失われる外部処理（整形ツール・翻訳ベンダー往復・コピペ） | 弱い（状態が消え、次の翻訳で人の訳を上書きしうる） | **強い**（本文に何も無くても状態は別ファイルに残る） |
| frontmatter マーカー | 本文（frontmatter 内）に残る | **同じく本文に残る**（外部化は未実装） |
| 見た目（画面にハッシュが出るか） | 出る | 本文には出ない（frontmatter には出る） |
| 原文を書き換えるか | 書き換える（初回 sync で全件） | **frontmatter は書き換える**（本文は書き換えない） |
| git の衝突 | ファイル単位に分散 | 1ファイルに集中（union merge で緩和） |

**要点**: embedded は「文書の中の変化」に強く「文書の外の処理」に弱い。external はその逆。external を既定にするなら、embedded が無料で持っている「文書の中の変化への追従」を、**別の手段で作り直す**必要がある。

なお ADR-260802-04 の「原文は初回同期でも1文字も書き換わらなくなる」は、**frontmatter を持つ文書では現状まだ達成できていない**（frontmatter マーカーは external でも原文に書き込まれる）。

## 7. 埋め方（改訂版）

満たしたい性質:

- **P-a**: ユニットの同一性は「何番目か」だけで決めない。
- **P-b**: ファイルの同一性はパスを第一候補にしつつ、**移動を追える**ようにする。
- **P-c**: **走査の副作用で状態を消さない**。追えなかったものは削除ではなく「要対応」に倒す。
- **P-d**: 迷子になった対応は**画面に出る**し、人が再リンクできる。
- **P-e**: どんな壊れ方からも `sync` で再構築できる（現行の不変条件を維持）。

### 順序（当初案から入れ替えた）

当初は「並べ合わせ（内容による住所の付け直し）」を最優先に置いていたが、設計レビューの結果、**先に「気づける」ようにするほうが安く、壊す危険も小さい**と分かったため順序を変えた。

| 段階 | 内容 | 効くもの |
|---|---|---|
| **0** | キー正規化の一本化と、「走査対象外 / 実体が無い / 導出した原文が無い」の**3分割**（§5 の (3)(4) の是正） | 以降の全段階の前提 |
| **1** | 孤立判定を「訳文から導出した原文が実在するか」で行い、**可視化しつつ削除を止める**。内容照合は不要 ※完了（§17） | ADR-260802-04 のゲートのうち「削除でなく要対応」「孤立を伝える」。**embedded の F-10 も同時に直る** |
| **2** | `onWillRenameFiles` で原文と訳文を**ペアごと動かす** ※完了（§18） | ゲートの「リネーム・移動で訳文が消えない」を構造的に満たす |
| **3** | ユニットの**並べ合わせ**（下記の制約つき）。ロードマップからは外し、保留席の基準だけを P03 として切り出した ※P03 完了（§19） | S3 / S4 / S5 / S13 などの誤対応 |
| **4** | 内容によるファイル再リンク（イベント取りこぼしの補助）。pair と role で候補を縛り、**双方向に一意のときだけ**移送 | VS Code の外で起きたリネーム |
| **5** | frontmatter の外部化と external 既定化 | ADR-260802-04 |

段階1の前に、`attachMarkers` の titleHash 不一致を debug ログから **sync 結果へ引き上げるだけ**でも、S3 / S4 / S5 は「静かに壊れる」から「壊れたと分かる」に変わる。最も安い一手として先に入れる価値がある。

### 段階3（並べ合わせ）の制約

当初案は「保存済みの行の `hash` といまの本文ハッシュが一致するものを錨にし、間を `titleHash` + `level` で埋め、残りは順序で埋める。**余った行・余ったユニットは対応なしとする**」だったが、レビューで2つの問題が出た。

**(a) 錨は「変わっていないユニット」にしか立たない。** 状態を守る必要があるのは変わった側で、そこでは必ず錨が外れる。つまりこの方式は「ズレが全域に及ぶ → 錨と錨の間の区間に閉じる」という改善であって、区間内の決定は今日と同じ順序当てのままである。単一操作（S3 / S4 / S5）は直るが、**同じ区間内で「挿入 ＋ 別の章を見出しごと書き換え」をやると同じ壊れ方が再現する**（S10 型）。「embedded 同等になる」は言い過ぎで、正しくは「単一操作は直り、複合操作は被害が区間に閉じる」。

**(b) 「対応なし」は訳文側に不可逆の壊れ方を作る。** `from` を失った訳文ユニットは `need:review` が永続化され、次回から**独立ユニット扱いで対応付けの対象から永久に外れる**。原文側は相手を失って新規扱いになり、同じ章が訳文にもう1本生える。しかも sync を回す前から、`from` の無いユニットは進捗の分母から消え、訳文向けの操作もツリーから消える。**今の index 当ては（誤っていても）必ず `from` を与えるので、これは並べ合わせが新規に持ち込む壊れ方である。**

したがって段階3は次の形に縮める:

- **訳文側では「対応なし」を作らない**。錨・`titleHash`・`level` で決まらなければ、最後は位置で当てる（＝今日の挙動へフォールバックする）。壊れ方を増やさないことを、直すことより優先する。
- **末尾行の刈り取りは条件つき**にする: ユニット数が 0 のときは刈らない（訳文を一時的に空にした・fence 崩れ・`sync.level` 変更の途中状態で全行が消える）、ctx が無いときは何もしない（`markers-migration` の中間 stringify が依存している）、将来の frontmatter 行（`order = -1` など）を巻き込まない。同時に `delete-unit.ts` の手動の後始末を外す。
- **embed（external → embedded 戻し）経路の手当て**: 当たらなかったユニットのマーカーを捨てる実装なので、並べ合わせを入れると `from`/`need` が本文にも store にも残らず消える。
- **受け入れテストに S24 / S25 を入れる**。同一本文の章が複数あると、保存済み行のハッシュ集合といまのハッシュ集合が完全に一致してしまい、「どちらが消えたか」をハッシュだけでは決められない。embedded がこれを解けるのは住所が内容ではなく**位置**だからで、並べ合わせには「区間内で余った側は末尾から捨てる」等の追加規則が要る。

より根本的な代案として、`unit-registry` に保存済みの**前回の原文本文**を使い、ハッシュ完全一致ではなく類似度で並べ合わせる案がある（形式変更は不要）。(a) の「編集されたユニットほど錨にならない」を正面から壊せるが、訳文本文は `unit-registry` に入っていないため訳文側にも同等の保管が要る。段階3を本気でやるならここまで踏む価値がある。

### 段階5（frontmatter の外部化）の注意

frontmatter まで外に出すと、external の Markdown は**mdait の痕跡を1文字も持たなくなる**。つまり「リネームされたファイル」と「新しく作られたファイル」が本文以外では区別できない。段階2（ペアごと動かす）と段階4（内容による再リンク）が、そのとき唯一の手がかりになる。

代案として「frontmatter に `mdait: id:` を1行だけ残す」も考えられる（パスの同一性が完全に解決し、行数は1本）。ただし「原文を1文字も書き換えない」という ADR-260802-04 の主目的とは正面からぶつかるため、内容による再リンクが実用に足りないと分かった場合の退避案として置いておく。

> **2026-08-05 決定（§16 の質疑）**: 今は線を越えない（id 行は書かない）。この決断は何もブロックしない — 段階1・2 は id の有無に関わらず必要で、id が効くのは「VS Code の外で動かされた」場合だけ。その頻度と段階4の的中率は実測してからでないと、原理を破る価値があるか判断できない。1行の id も「ハッシュを操作できない層に『これは何か』を問わせる」問題を規模が小さいだけで再生産する。**再訪条件**: 段階4を入れたあと、実運用で「再リンクが決められず孤立のまま残る」事例が観測されたら opt-in 設定として検討する。

## 8. 実装前に決めておくこと

- **「孤立」の定義を3分割する**: (a) 行があるのに実体が無い、(b) 実体はあるが導出した原文が無い、(c) 今回の走査スコープ外（未選択の pair・拡張子外・sparse checkout・ブランチ切替）。**(c) を孤立に混ぜない**。これを決めないと §5 の (3)(4) が全部誤検出になる。
- **孤立行のライフサイクル**: 明示破棄のみか、N回連続で孤立なら退避か。退避ファイルを作るなら `.gitignore` / `.gitattributes` の冪等生成への追加と、union merge で復活する行の扱い。
- **`cleanupOrphans` の本来用途の代替**: 元の目的は「extensions 設定変更後の残留掃除」。消さないなら、いつ誰が消すのか。
- **安全弁の分母**: 「全行」ではなく **pair × ロール（原文/訳文）ごとの、今回走査したスコープ内の行数**。絶対件数の下限も要る（1〜2件で比率に騙されない）。
- **再リンクの判定基準**: 被覆率か Jaccard か、最小ユニット数、空ファイル・1ユニットファイルの除外、pair と role による候補制限、双方向一意性、移送後の order 再割当。「十分重なる」のままでは実装者ごとにぶれる。**未翻訳の訳文は原文の丸写しなので、role で縛らないと原文の行が旧訳文へ吸い込まれる。**
- **並べ合わせの規則の定式化**: 単調性とタイブレーク（「元の order に近い方を優先」との両立）、`titleHash` + `level` を両方一致に限るか（レベル変更を救うなら緩和順が要る）、区間内に同一 `titleHash` が複数あるときの扱い。
- **イベント順序と排他**: `syncCommand` は毎回 `load()` を無条件に呼びメモリ上の変更を捨てるため、リネームハンドラが save せずに終わると**無言で状態を失う**。sync 実行中に届いたリネームの保留も要る。ストア単位のロックは存在しない（`FileMutex` はファイルパス単位）。→ **解決済み（§18）**: `infra/workspace/unit-state-lock.ts` を新設し、`syncCommand` / `syncSingleFile` / `relocateUnitEntries` が同じ区間で直列化する。
- **再リンク／破棄をどの経路に置くか**: ADR-260726-01 の不変条件（排他・ストア保存・ステータス更新は `unit-mutation.ts` にしか無い）に従い、`FileHandler` のメソッドとして足す。サーフェスが `UnitStateStore` を直接触るのは禁止。旧パスと新パスの2つに触るため、`withFileMutation` の複数パス版が要る。
- **サーフェスの割り当て**（ux.md §3.3）: 状態＝ツリー（「原文と結びついていない訳文」ノード）、操作＝ツリー行のインライン、解説＝Hover、気づき＝ステータスバー。破棄は破壊的なので modal 確認。孤立が解消されるまで毎回通知を出さない。
- **sync は訳文ディレクトリを列挙していない**。孤立の検出を sync に載せるなら列挙の新設が要る（コストと ignore パターンの扱いも決める）。

## 9. 現時点の結論

- external は `markers.mode` を切り替えれば動くが、**章の挿入・削除・並べ替えに対して静かに壊れる**。しかも壊れた対応が保存され、次の翻訳で本文に及ぶ。実測では**訳文の本文そのものが消えるケース**（S25 / S30 / S34）まで確認した。
- 壊れは累積しないが自己修復もしない。sync を何度流しても同じ壊れた状態に固定される。
- リネーム・移動・原文削除では状態が消えるが、訳文の本文は残るため復旧は `review` からのやり直しで済む。危険度は挿入・削除より低い。
- ただし**原文だけをリネームすると、旧訳文が孤立したうえに未翻訳の複製訳文が生成される**。これはペアがパスから導出されているためで、**embedded でも同じように起きる**。unit-state の行を追随させるだけでは直らない。
- 直すのに外部ファイルの形式変更は要らない。ただし**並べ合わせだけでは embedded 同等にはならず**、やり方を誤ると新しい不可逆の壊れ方を作る。先に「気づける」ようにし、次に「ペアごと動かす」ほうが安い。
- 調査の副産物として、**マーカーの保管方式と無関係に frontmatter の翻訳が永久にスキップされる欠陥**（§5-(1)）が見つかった。こちらは external 化と切り離して直すべきである。

## 10. 実装したこと（2026-08-03）

### 変えたこと

**行とユニットの突き合わせを、番号ではなく内容で行うようにした。**

1行は「前回 sync した時点でのそのユニットの姿」の写しなので、対応づけは「前回の並び ↔ いまの並び」を
突き合わせる問題になる。これは原文と訳文を突き合わせる `SectionMatcher` と同じ形をしているため、
共通部分を `core/matching/interval-align.ts` に純粋関数として切り出し、`core/unit-state/unit-state-align.ts`
から使っている。

手がかりは強い順に3つ。

1. **本文の hash の一致**。行にも1つ、ユニットにも1つしかない hash は身元が確定しているので、
   **順序が入れ替わっていても採用する**（章を並べ替えても対応が入れ替わらないのはこのため）。
   同じ hash が複数ある場合だけ、前後の確定した対応との順序関係で決める
2. **見出しの hash とレベルの一致**（＝本文だけ書き換えられた章）
3. 確定した対応と対応のあいだでの**順序**（＝見出しごと書き換えられた章）

あわせて、**ユニットが減ったときに末尾の行を刈る**ようにした（`pruneEntriesFrom`）。
ただしユニットが 0 件のときは刈らない（本文を一時的に空にした・パース途中の崩れた状態で、
そのファイルの行を丸ごと失わないため）。`delete-unit.ts` の手作業の後始末も同じ API に寄せた。

### 「わからない」を表す新しい状態は作らなかった

当初は「対応が不明」を表す need を足す案だったが、**区間内を順序で埋める段があるため、
訳文のユニットが対応相手を持たないまま残るのは「その区間で本当にユニットが増えている」ときだけ**になった。
つまり `from` を失って独立ユニット化する片道切符は生まれない。語彙を増やさずに済んでいる。

### どこまで直ったか（実測）

`scripts/exploratory/probe-robustness.js` は最後に**両モードの結果を突き合わせ、想定外の差があれば
終了コード 1 を返す**ようにした。差が出てよいシナリオは理由つきで `EXPECTED_DIFF` に列挙してある。

```
一致 23 / 想定内の差 8 / 想定外の差 0
```

**ファイル内の編集（S1〜S5・S13・S20〜S27・S29〜S35）はすべて embedded と完全一致**になった。
とくに次の3つは、実測で「訳文の本文が消える」「同じ訳が2箇所に居座る」だった。

| # | 変更前（external） | 変更後 |
|---|---|---|
| S13 | 訳文に第3章が二重に残り、第1.5章の訳が生まれない | 新章が正しい位置に訳出され、他は無傷 |
| S25 | 第3章の訳が消滅し、同じ「注意事項」の訳が2箇所に居座る | 正しい方だけが消え、他は無傷 |
| S30 | 第3章の訳が消滅し、原文に無い H1 が居座る | 導入の訳だけが消え、他は無傷 |

残る差はすべて**ファイルの同一性（パス）**に関わるもので、これは行の中の話ではないため今回の対象外。
`docs/ux.md` の F-10（リネームで訳文が孤立する）と同じ問題で、embedded にも存在する。

### まだやっていないこと

- **`SectionMatcher` を共通の核に載せ替えていない。** 切り出した `interval-align` を使っているのは
  external の attach 側だけである。`SectionMatcher` の区間処理は「原文の hash を持つ訳文は
  区間内の位置合わせに使わない」といった固有の条件を抱えており、載せ替えは同値性の確認を伴う別作業になる。
  両モードの結果一致をプローブが見張るようになったので、その安全網の上で進められる
- ファイルのリネーム・移動・削除への追随（§7 の段階1・2・4）
- §5 に挙げた、保管方式と無関係の欠陥（frontmatter の翻訳が同じ内容に戻るとスキップされる、など）

## 11. 敵対的レビューで見つかった穴と、その後（2026-08-03）

**§10 の「ファイル内の編集はすべて embedded と完全一致」は誤りだった**。以下は訂正と対応。

### 直したもの

| 見つかった穴 | 症状 | 対応 |
|---|---|---|
| 章を移動したうえで編集すると対応を失う | 見出しもレベルも一致しているのに、確定した対応が交差して区間の枠が崩れ、行とユニットが別々の区間に落ちて照合されない。**訳文の本文が消える**（実測 S51/S59/S60） | 「見出しの hash とレベルが両側で一意なら順序を無視して採用する」段を足した（＝本文 hash と同じ規則を弱い鍵にも適用） |

| | 一致 | 想定外の差 |
|---|---|---|

## 12. 「知らないものは消さない」（2026-08-03）

状態を**静かに消す**箇所が3つ見つかった。どれも同じ形の間違いで、**見えていないものを「無い」と断定して消していた**。
ユーザーは気づかず、復旧手段が無い。ADR-260803-03 として記録した。

### 直したもの

| 箇所 | 何が起きていたか | どう直したか |
|---|---|---|
| **sync の孤立掃除**（`sync-command.ts` → `UnitStateStore`） | 選択中の pair だけを走査して作った「生きているパスの一覧」に無い行を全削除。ja→en だけ選んで sync すると **fr の行が丸ごと消えた**（実測 S62 / S63） | 範囲を3分割して判断する（下記 §13）。**config のどのペアの配下にも無い行は消す／config にあるが今回走査していない行は残す／走査して見つからなかった行は消す**（`cleanupOrphansInScope`） |
| **embed（external → embedded 戻し）**（`markers-migration.ts`） | hash の無いユニットのマーカーを捨てたうえで、**そのパスの全行を削除**。対応の付かなかった行の `from`/`need` が本文にも store にも残らなかった。しかも `reconcileMarkerModeForFile` 経由で **sync のたびに走る** | `alignEntriesToUnits` で「どの行がどのユニットへ書き戻されたか」を出し、**書き戻せた行だけ**を消す。残した行は警告に出す（セッション内で1ファイル1回） |
| **末尾行の刈り取り**（`marker-provider.ts` の `detachMarkers`） | ガードが `units.length > 0` だけ。守りたいのは「0件」ではなく「**一時的に減った**」ケース（コードブロックの閉じ忘れ・`sync.level` 変更）。刈った後は設定を戻しても状態は戻らない | `shouldPruneTail`: **半分未満へ3件以上減った**ときは刈らず、**保留席へ移す**（§13）。比率だけだと2件→1件で止まるので絶対件数の下限を併せる |

### なぜ「残す側」に倒すか

**消す側の失敗は取り返せず、残す側の失敗は取り返せる。** これが判断の根拠である。
ただしこの非対称が成り立つのは、**残した行が勝手に別の章へ結ばれないと保証できるとき**だけである。
その保証の作り方は §13 に書いた（初版の「内容が一致しないかぎり拾われない」という説明は誤りだった）。

embed だけは「全部残す」ではなく「書き戻せなかった行だけ残す」にした。全部残すと、本文（これ以降の正）と
store が二重に状態を持ち、embedded 運用のあいだ静かに古くなるためである。

### 併せて直したこと: キー正規化の一本化（§5-(4)）

孤立判定に渡すパスを `toWorkspaceRelativePath`（＝行のキーと同じ基準）に統一した。非MDだけ
`FileExplorer.normalizePath`（設定ベースディレクトリ基準）だったため、カスタム config パスでは
両者が食い違い、非MDの行が毎 sync 全滅していた。食い違うこと自体を単体テストで固定してある。

あわせて MD のパスも**マーカー保管方式に関わらず**収集するようにした。embedded 運用でも、embed で
本文へ書き戻せなかった行がストアに残ることがあり、それを掃除で消してしまわないため。

### 警告をどこに出すか

刈り取りを見送ったことは**ログにだけ**出す。`detachMarkers` は core にあり、サーフェスを呼べない。
それ以前に ux.md §3.3 の「変化のたびにトーストを出さない（通知疲れの回避）」に反する。
そもそも**何も壊れていない**（状態は守られている）ので、気づきを要求する出来事ではない。
繰り返し起きるようなら doctor 診断に載せるのが筋だが、今はまだ要らない。

### まだやっていないこと

- 孤立行のライフサイクル（§8）。いまは「範囲内で実体が無ければ即削除」のまま。退避や N 回連続での判定は入れていない
- 走査範囲の粒度はディレクトリ止まり。ignore パターンで除外されたファイルは「範囲内で見つからなかった」扱いになる（従来どおり）
- **`UnitStateStore` に `path → 行` の索引が無い。** `getEntriesByPath` / `countEntriesByPath` /
  `parkEntriesFrom` はどれも全行を舐める。detach ごとに1回増えたが桁は変わらないので今回は据え置いた。
  1ファイルあたりの行数ではなくワークスペース全体の行数に比例するため、規模が上がるなら索引を持つのが筋である

## 13. 敵対レビューで見つかった、§12 自身の穴（2026-08-04）

§12 の初版には**前提が事実と食い違っている**箇所が2つあり、どちらも回帰になっていた。

### (1) 「残した行は内容が一致しないかぎり拾われない」は誤り

突き合わせには**順序だけで機械的に埋める段**がある（`interval-align.ts` の `fillGaps`。§10 の手がかり3つめ）。
手がかりの残っていない行とユニットは、内容が1文字も一致しなくても区間内の順番で結ばれる。
つまり刈らずに残した行は、あとから章が増えたときにその章へ貼り付く。

実測: 8ユニットの文書から6章消して sync（＝刈り取りを見送る）し、そのあと新しい章を1つ足すと、
新章の need が embedded では `translate` なのに external では **`revise@（削除済みの第2章の原文hash）`** になった。
`revise` は「旧原文と新原文の差分を取って既存訳を直す」流れなので、AI に無関係な章の差分が渡る。

**直し方: 残す行は「保留席」へ移す。** 刈らないと決めた行の `order` を `HELD_ORDER_BASE`（100万）以降へ
付け替える。こうすると「いまの本文のどこにも対応する場所が無い行」だと**行そのものから分かる**ので、
順序で埋める段から確実に外せる。内容（本文の hash・見出しの hash とレベル）で当てる段は従来どおり
動くので、章が戻ってくれば正しく復帰する。

覚える場所を order 列に作ったのは、**列を増やせない**ためである（7列ちょうどでない行はローダーが
警告なく全部読み飛ばす）。実運用のユニット数とは桁が違うので、生きている order と衝突しない。

比率で推し量る案（「行がユニットの倍以上あるあいだは順序を信用しない」）も試したが、
ユニットが少し増え戻るだけで regime を抜けてしまい、同じ貼り付きが再現した。覚えるしかない。

### (2) 掃除の軸を「走査したか」にしたため、掃除が永久に効かなくなった

「走査していないディレクトリの行は残す」だけにすると、**ペアを config から外した**・
**ディレクトリを改名した**ときに旧パスの行が二度と走査されず、永久に残る（実測で確認）。

**直し方: 軸を2つに分ける。** 選択は一時的なもの、config は恒久的なものなので、両方を見る。

| 行の位置づけ | 判断 | 対応する状況 |
|---|---|---|
| config のどのペアのディレクトリにも属さない | **消す** | ペアを設定から外した／ディレクトリを改名した |
| config にはあるが今回走査していない | **残す** | 未選択の pair／sparse checkout／ブランチ切替 |
| config にあり走査もしたが見つからなかった | **消す** | `trans.extensions` を変えて管理対象から外れた |

これは §8 の「走査対象外／実体が無い／導出した原文が無い」の3分割と素直に対応する。
`transPairs` が空のときは何もしない（設定が読めていない状態で全行を消しかねないため）。

### (3) 「ディレクトリは在るが0件」を「全部消えた」と読んでいた

走査したことの登録がファイル列挙の**前**にあったため、原文を一時的に退避しただけで
そのペアの全行が消えていた（S62 / S63 で直したのとまったく同じ症状）。登録を列挙の後ろへ移した。
副産物として **S6〜S9 のうち S9（原文ファイルを削除）が embedded と一致するようになった**。

### 原文ディレクトリごと無いときに行が守られる本当の理由

`getSourceFiles` が throw して **sync 全体が止まる**からである。掃除側の分岐で守っているわけではない
（実測: 先頭ペアの原文ディレクトリを消すと、後続ペアも1件も処理されない）。
初版にあった「このペアの掃除だけ飛ばす」分岐は到達しないので削除し、コメントを実態に合わせた。

### 防波堤

- **probe（S64・S65・S66）**: 保留した行が新章に貼り付く／往復（external→embedded→external）で状態が
  失われる／0件走査で行が消える、をそれぞれ embedded との突き合わせで検出する。巻き戻すと落ちることを確認済み
- **sweep（P7）**: C-2・C-3 の防護そのものは **probe の突き合わせでは観測できない**（C-2・C-3 を
  巻き戻しても probe は `想定外の差 0` のまま終了コード 0 で、sweep P7 だけが落ちることを確認済み）。

  理由は当初「崩れたユニット列が detach に届かないから」と書いていたが、**これは誤りだった**。
  フェンスを閉じ忘れた原文を `syncCommand` に通すだけで保留席が14行できる（保留席は `detachMarkers`
  からしか作られないので、崩れた列は確かに届いている）。

  本当の理由は「**届いた先の行に、突き合わせで見える価値が残っていないから**」である。
  原文側の行は `from`/`need` が空で hash は本文から再計算できるので、消えても復帰しても見え方が変わらない。
  訳文側は、行が守られる前に**本文のほうが自動削除で消えていた**（§14 の最優先項目そのもの）ので、
  行の有無に関わらず結果が同じになる。だから sweep でその形を直接叩いて
  「行が減らない」「embed が書き戻せない行を消さない」を assert する

### 現在地（§13 時点）

```
一致 47 / 想定内の差 9 / 未修正の既知欠陥 2 / 想定外の差 0   （probe）
```

その後 §14 でシナリオを足し、S9 の題材を直したため数は変わっている（最新は §14 の末尾）。

## 14. 台帳を守って本を燃やしていた（2026-08-04）

3周目のレビューで、**保留席が守ろうとしている筋書きそのもので、守るべきデータが既定設定で
先に消えている**ことが分かった。仕組みは正しく動いていたが、置かれている文脈が間違っていた。

### (1) 【最優先】原文のフェンス1つで、訳文が物理削除されていた

ADR-260803-04 は保留席の存在理由を「フェンスの閉じ忘れでパースが崩れたとき、刈ると
`from`/`need` が戻らない」と説明していた。その筋書きを**既定設定**（`sync.autoDelete: true`）で
実際に走らせた結果が次である。

```
[崩す前]  訳文の章数 = 7
[崩した後] 訳文の章数 = 0     ← 訳文の本文が物理削除された
          保留席 = 14 行      ← 行だけは守られている
[直した後] need = [revise, translate ×7]   ← 訳は戻らない
```

原文にフェンスの閉じ忘れが1つ入ると、以降の見出しが全部コードとして飲まれて1ユニットになる。
訳文の章はまとめて「原文を失った」状態になり、`sync.autoDelete: true`（既定）では**物理削除**される。
保留席は行を守るが、**守られた行が指している訳文はもうディスクに無い**。git からしか戻せない。

`autoDelete: false` にすると本文は残るが、今度は直したあとも全ユニットが `verify-deletion` のまま残った。

**直し方: 行に当てた原則を本文にも当てる。**

- **崩れを疑ったとき（`isSuspiciousShrink` が真）は孤立ユニットの自動削除をしない。**
  判定は行の刈り取りと**同じもの**を使う（`core/matching/shrink-guard.ts` に切り出した）。
  行だけ守って本文を消していては原則が成立しないので、疑うかどうかの基準は1つでなければならない
- 止めるときは黙って残すのではなく `verify`（`need:verify-deletion`）へ倒す。削除が本当に正しければ
  人が確定でき、`need` の語彙も増やさずに済む
- **原文が戻ってきたら `verify-deletion` を自動で解除する。** 「削除してよいか確認して」の前提が
  消えたのだから残してはいけない。これが無いと、フェンスを直したあとも確認待ちが残り続けた

判定は「訳文のユニットのうち、どれだけが対応を失ったか」で行う。原文側の前回の数を使わないので
embedded / external のどちらでも同じように効く。実際、フェンスのシナリオでは**両モードとも**
章が完全復帰するようになった。

代償: 原文から本当に章をまとめて消したとき（8章のうち5章など）も自動削除されず、確認待ちになる。
訳文を消すのは取り返しがつかないので、確認を挟むほうを選んだ。`orphanTargetPolicy: verify` を
常時使う運用と同じ状態になる（出口の課題は下記 (6)）。

#### 慎重さの度合いは用途で変える（3周目の追補）

最初は刈り取りと削除で**同じ閾値**（減少幅3件以上かつ半分未満）を使ったが、これは刈り取り側の
理屈で決まった値だった。「行が2件から1件に減るのは普通の編集」は正しいが、
**「訳文2件が消える」は「行2件が余る」とは重みが違う。**

その結果、小さい文書ではガードが一度も効いていなかった（実測、両モードで同一）。

| 訳文のユニット数 | フェンス閉じ忘れの結果（修正前） |
|---|---|
| 2 | 訳文 1 件を物理削除 |
| 3 | 訳文 2 件を物理削除 |
| 4 以上 | 守られる |

**見出し2つの README で、原文にフェンスの閉じ忘れが1つ入ると訳文の2節が消える。**
「最優先」として直したはずの事故が、文書が小さいというだけで素通りしていた。

**述語は1つのまま、慎重さだけを用途で切り替える。** 根拠は閾値の恣意性ではなく、
**間違えたときの代償が非対称**であること。

| 用途 | 疑いそこねたときに起きること | 取り返し |
|---|---|---|
| 刈り取り | 行が1本余分に残る | **つく**（次の刈り取りで消えるし、内容が一致すれば復帰する） |
| 自動削除 | **訳文が物理削除される** | **つかない**（git からしか戻らない） |

削除側には「**対応が1件以下しか残らなかったら、減少幅が1件でも疑う**」を足した
（`DELETE_SUSPICION.collapsedRemainder = 1`）。**崩れは文書の大きさに関係なく1ユニットまで潰す**ので、
崩れの見分けどころは「残りがほとんど無い」であって「たくさん減った」ではない。守られるかどうかが
元のユニット数だけで決まる状態は設計ではなかった。

実測（修正後、両モードで同一）: 2・3・4・5ユニットのいずれもフェンス崩れで訳文が消えず、
直せば `verify-deletion` も解ける。原文を空にした場合（1・2・3ユニット）も守られる。
**普通の編集は自動削除のまま**（8ユニットから1章削除 → 見出し 8→7、確認待ち 0 件）。

#### 何を数えるか — 「対応が付いた数」ではなく「原文のユニット数」（4周目の訂正）

`collapsedRemainder` を入れた最初の版は、**対応が付いた数**（訳文のユニット数から孤立を引いた数）を
見ていた。これが小さい文書で誤爆する。統合時に B のテストが捕まえた。

| 場面 | 原文のユニット数 | 訳文のユニット数 | 対応が付いた数 | 対応の数で判定 |
|---|---|---|---|---|
| フェンス崩れ（本物） | **1**（8から潰れた） | 8 | 1 | 疑う ✓ |
| 2ユニットの1章を編集 | **2**（潰れていない） | 2 | 1 | 疑う ✗ **誤り** |

誤爆すると古い章が `need:verify-deletion` として本文に残り、**訳文に同じ章が2つ並ぶ**。

```markdown
## 第1章
第1章の本文（改訂）。

<!-- mdait ... need:verify-deletion -->   ← 重複した古い第1章
## 第1章
第1章の本文。
```

**「崩れ」の本質は原文の構造が潰れたことなので、原文のユニット数を見る。** 判定を
`isSuspiciousShrink(管理下の訳文ユニット数, 下流へ出る原文ユニット数)` に替えた。上の表なら
フェンス崩れは 8 対 1 で潰れており、編集は 2 対 2 で潰れていない。どちらも**いまの数**しか
使わないので、前回の状態を持たない embedded でも同じように効く（この性質は維持している）。

分母から外すもの: 独立ユニット・`need:isolate`・マーカーなしの管理外コンテンツ（もともと自動削除の
対象ではないため）。分子から外すもの: `need:isolate` の原文（下流へ伝播しないため）。

**この誤爆が起きる条件は「原文がマーカーを失っていること」。** 編集された章は本来
`source.marker.hash`（＝前回のハッシュ）と訳文の `from` が一致して結ばれる。原文をバックアップや
git から書き戻すと本文のマーカーが落ち、`ensureMdaitMarkerHash` が**いまの**ハッシュを合成するため
一致しなくなり、「孤立1件＋新規1件」になる。`.mdait` を git 管理外にしている運用・新しいクローン・
キャッシュ削除でも同じ形になるので、事故ではなく普通に起きる。

なお `unit-registry` は無関係だった。`SectionMatcher` も `sync_CoreProc` も対応付けに registry を
参照していない（registry への書き込みはスナップショット保存と note の移送・GC のためだけ）。
同じ registry 状態で、マーカーを保ったまま編集した場合は再現せず、マーカーを落とした場合だけ
再現することを単体テストで切り分けてある。

**伝え方**（ux.md §3.3）: 「何も起きなかったように見える」と困る場面なので、ログだけにはしない。
通知に載せてよいのは「実行の結果と、結果に対する次の一手」であり、これは sync の実行結果そのもの
（＝訳文を消さずに確認待ちにした）なので通知が正しい。件数と入口だけを示し、個々の状態はツリー
（`need:verify-deletion` のユニット）で受け取る。明示実行の sync だけが出す（`autoSyncOnSave` は
`syncSingleFile` 経由で通知を出さない）。

### (2) 【重大】`sourceDir: "./content/ja"` と書くだけで行が全部消えていた

同じディレクトリを指したまま**表記だけ**変えると、訳文側の行が sync 1回で全滅していた。

正規化された文字列同士は前方一致で「配下かどうか」を判定される（`isPathInDirectory`）ので、
**同じ場所を指す表記は必ず同じ文字列にならなければならない**。`FileExplorer.normalizePath` は
絶対パスしか畳んでおらず、`"./content/ja"` や `"content/ja/"` はそのまま返っていた。その結果:

- `configuredDirs` / `scannedDirs` は `path.resolve` で正規化されるので「走査した」と登録される
- `getTargetPath` は前方一致に失敗して **null を返す**（＝1ファイルも同期されない）
- 訳文パスが `seenPaths` に入らないまま「走査済み」だけが立ち、区分3（走査したが見つからない）で削除される

`validateForRun` は `"./docs"` を正当な書き方として明示的に想定している。**設定バリデーションが
通す書き方で状態が消えていた。** `normalizePath` で相対パス表記も畳むようにした（C-5 でやり残していた
3つめの正規化基準）。

### (3) 保留席の寿命（当時は変えなかった。**2026-08-09 に §19 で変更**）

保留席の order は必ず `units.length` より大きいので、`pruneEntriesFrom` が一度でも走ると全部消える。
`shouldPruneTail` はユニット数が保留席の数に追いつくと真になるため、**「章が戻ってくれば復帰する」には
ユニット数で測る締め切りがある**。

```
6章削除直後:      live=4  held=12
新章を1個足した:  live=6  held=12
…
新章を4個足した:  live=12 held=0    ← 12行がここで消える
```

`delete-unit.ts` の刈り取り（ユニットを1つ消す操作）も同じ経路を通り、そのファイルの保留席を全部消す。

**寿命は変えない。** 保留席は「崩れが直るまでの待避所」であって恒久的な保管場所ではない。
ユニット数がそこまで戻っているなら、それは崩れではなく本当の編集だったと見るのが自然である。
恒久的に持つなら退避ファイルなど別の仕組みが要る（§8 の宿題）。

> **【2026-08-09 追記】この判断は §19 で覆した。** 保留席の役目が「崩れが直るまでの待避所」から
> 「**その章の本文が戻ってくるまで状態を預かる場所**」へ変わったため、ユニット数で測る締め切りが
> 成り立たなくなった。sync は原文から消えた章を作り直すので、章を1つ消しただけでユニット数は
> 即座に元へ戻る。締め切りを残すと、預けたその瞬間に席が消える。詳細は §19 と ADR-260809-01。

**ただし消すときは記録する。** `pruneEntriesFrom` はログを1行も出していなかった。掃除は debug を、
刈り取り見送りは warn を出すのに、実際に状態を失う操作だけが無言だった。info を出すようにした。
併せて、刈り取り見送りの warn は**新たに保留した行があるときだけ**出す（保留席がある状態は安定なので、
毎 sync 同じ警告を積むと読む価値が無くなる）。

### (4) S9 の題材を直した — 挙動はディレクトリの中身の数で変わる

S9（原文ファイルを削除）が embedded と一致したのは、プローブの題材が原文1ファイルだけで、
削除すると `content/ja` が0件になり「走査していない」扱いで行が残っていたからでしかない。
**原文を2ファイルにして片方だけ消すと一致しない**（external は状態を全部失う）。

題材を2ファイルに変えて実態を測るようにし、`EXPECTED_DIFF` に理由つきで戻した。
「最後の1ファイルを消したときだけ状態が残る」という挙動の非対称も、その理由に書いてある。

### (5) 残存リスク（記録のみ）

**自動削除を見送るようにした以上、確認待ちを日常的に発生させることになる。** これまでは既定設定で
確認待ちがそもそも出なかったので目立たなかったが、今後は正当な一括削除のたびに列ができる。
その出口が2つとも細い。今回の変更を差し戻す理由にはならないが、次に手を付けるならここである。

**(a) `Keep` は次の sync で元に戻る**（`section-matcher.ts` の孤立ターゲット処理。既存挙動）

```
第3章を削除して sync : need=verify-deletion
Keep 実行            : need=-              ← 消えた
そのあと sync        : need=verify-deletion ← 復活した
```

`Keep` は need を外すだけで `from` を残すため、次の sync が「原文を失った訳文」として再び拾う。
恒久的に残す方法は「独立ユニットにする」（`from` を外す）で、設定ドキュメントには書かれているが、
**ツリーと CodeLens は Keep / Delete の2択として提示していて、Keep が一時的だとはどこにも出ない。**

**(b) 確定は1ユニットずつしかできない**

`mdait.unit.delete` はユニット行にしか付いておらず、ファイル単位・フォルダ単位の一括確定が無い。

## 15. 「文書の読み取り」側の修正（2026-08-03〜04）

§11 で残った欠陥は、突き合わせアルゴリズムの外側 — **本文をどう読み、どう書き戻すか** — にあった。

### コードブロックの中身は本文であって、マーカーではない（S55 / S58）

壊れ方は2段階だった。

1. **パーサーがコードブロックの中身を書き換えていた。** `normalizeMarkerSpacing` は
   「マーカー行の直前に空行が無ければ挿す」処理だが、行を生の正規表現で判定しており
   コードブロックの中も対象にしていた。利用者が書いた見本のコードブロックに空行が生えていた
   （design.md P9 の適用漏れ）
2. **trans がコードブロックを行の途中に戻していた。** AI へ渡す前にコードブロックを
   `__CODE_BLOCK_PLACEHOLDER_n__` へ退避し、戻すときは単純な文字列置換だった。
   AI がプレースホルダを前後の文とつなげて1行にまとめると、開始フェンス（```）が行頭に来ず
   **コードブロックでなくなる**。すると中身の `<!-- mdait ... -->` と `## サンプル章` が本文として
   読まれ、偽のユニット境界ができる。embedded は `from` の当たらないユニットとして本文ごと削除し、
   external は見出しが1つ増えて行とユニットの対応が全域でずれ、無傷の訳文まで `need:translate` に倒れていた

直し方はどちらも一点に帰着する。**コードブロックの中身は本文である**。
そして「どこがコードブロックか」に答える場所を1つにする。

- パーサーの `normalizeMarkerSpacing` は `getCodeBlockLineSet` でコードブロック行を除外する
- trans の退避（`protectCodeBlocks`）も判定を `getCodeBlockLineSet` に寄せた。
  独自の正規表現 `/```[\s\S]*?```/g` は ```` ``` ```` しか見ないため、**`~~~`・字下げ
  コードブロックを素通りし、4連バッククォートを誤分割する**。素通りするとブロックの中身が
  そのまま AI へ渡り、S55/S58 と同じ壊れ方（訳文の本文喪失・全ユニット `need:translate`）が
  そのまま再現する。同じ問いに2つの答えを持たない
- 退避は**行まるごと**で行う。リスト項目や引用の中のコードブロックは行頭に字下げや `> ` が
  付くため、バッククォートの位置から切り出すと前置きがプレースホルダの手前に残る。
  すると戻すときに「行の途中だ」と誤判定して改行を挿し、**引用の中では閉じフェンスが
  `> ``` ` のままになって閉じない**（以降の見出しがすべてブロックに飲まれる）
- trans の復元（`restoreCodeBlocks`）は、AI がプレースホルダを前後の文につなげたときだけ
  行頭・行末へ来るよう改行を補う。ブロックが前置きごと退避されているので、補った改行の
  直後には元の字下げ・引用記号がそのまま来る
- 復元は「戻せなかったプレースホルダ」を返し、AI がプレースホルダを消した場合に
  警告として積む（コードブロックが黙って消えるのを防ぐ）
- 探索スイープ（`run-sweep.js`）の走査も同じ理由でコードブロックを除外した
  （除外しないと見本のマーカーを本物と数え、この文書を足した途端に誤検知する）

### Markdown の規則を Markdown でないファイルに当てない

`trans.extensions`（`.txt` など）の翻訳は `plain-file-handler` がファイルの中身をそのまま
`translator.translate()` に渡すので、退避も同じ経路を通る。ここに Markdown の
**「行頭を4スペース字下げしたらコードブロック」**という規則を当てると、
ただ字下げしただけの本文（アウトライン、`変更点:` の下の箇条書き）がコードと見なされ、
AI に渡らず**訳文に原文がそのまま残る**。実測で最大 80% の行が翻訳から外れた。

しかも**この経路には気づく手段が無い**。`plain-file-handler` は `TranslationChecker` を通らず、
ファイルがユニットに割れていないので構造の食い違いも検出できない。

そこで `protectCodeBlocks` に `markdown` オプションを足し、Markdown 以外では

- **字下げコードブロックを見ない**（`getCodeBlockLineSet` の `includeIndented: false`）
- **閉じていないフェンスは退避しない**（`~~~` や ``` で始まる行がたまたま在っただけの可能性が高く、
  末尾まで翻訳から外すと本文が丸ごと原文のまま残る）

ようにした。`.txt` に ```` ``` ```` で囲んだブロックが在ればこれまでどおり退避する
（旧実装が保護していた範囲は落とさない）。判定は `TranslationContext.fileExtension` を見る。

**「そもそも退避しない」を選ばなかった理由**: 旧実装は拡張子に関係なく ```` ```…``` ```` を
保護していた。退避をやめると `.txt` に書かれたコード例が翻訳されてしまい、別方向の退行になる。
最小の変更は「Markdown 固有の規則だけを外す」ことである。

「Markdown かどうか」の判定は `resolveFileTypeFromExtension`（拡張子から種別を決める唯一の定義）
へ委ねる。ここで独自に拡張子を並べると、`PlainFileHandler` が plain として扱うファイル
（`.markdown` / `.mdx`）に退避だけ Markdown の規則が当たり、同じ症状が別経路で復活する。

あわせて `plain-file-handler` が捨てていた `result.warnings` を拾うようにした。
コードブロックが AI に消されたときに「黙って完了」にならない受け皿がこの経路にも要る。

ただし **`need:review` を立てる条件は「コードブロックが戻せなかった」だけ**にする
（`TranslationResult.droppedCodeBlocks`）。「警告があること」を条件にすると、
JSON 混入検出（`sanitizeTranslationOutput`。AI が応答のエンベロープを漏らしたことを
捕まえる道具）が **`.json` ファイルや JSON の例を含む `.txt` で定義上つねに発火**し、
訳すたびに `review` が立つ。`need` を乱発すると、確認という仕組みそのものが信用されなくなる。
警告そのものは `logger.warn` に残す。

なおこの偽陽性は**探索スイープでは測れない**。フェイク AI が出力から波括弧を落とすため
JSON 混入検出がそもそも発火しないからで、既定の検査では見えないノイズだった。
条件の回帰は単体テスト（`plain-translation-review.test.ts`）で守っている。

### 残っている穴（直していない）

- **非 Markdown で、種類の違うフェンス（```` ``` ```` と `~~~`）が空行なしで隣接すると、
  両方とも退避されない。** 連続したコードブロック行をひとまとまりとして扱い、
  そのまとまりが「閉じたフェンス」かを最初と最後の行で見るため、種類が混ざると閉じ判定に失敗する。
  被害は「`.txt` のコード例が翻訳される」だけで、往復は1バイト一致のまま
  （本文の消失も構造の破壊も起きない）。頻度も低いので直していない

**証拠の内訳**（何がどこまで裏づけられているか）:

| 修正 | 裏づけ |
|---|---|
| trans の退避・復元 | プローブの突き合わせ（巻き戻すと S55・S58 が不一致になる）＋ 絶対チェック S72〜S74 ＋ 単体テスト |
| パーサーの `normalizeMarkerSpacing` | **単体テストのみ**（`parser-code-block-marker.test.ts`）。これだけ巻き戻してもプローブの想定外の差は0のまま — 空行の挿入は両モードに同じように効くため差にならない |

### プローブで見つからないもの

**プローブは embedded と external の結果を突き合わせる相対的な検査なので、
両モードが同じように壊れている欠陥は差として出ない。** 実際、上に挙げた
「リスト・引用の中のコードブロックが壊れる」回帰は両モード共通のため、
突き合わせでは最後まで検出できなかった。

そのため、結果そのものを見る**絶対チェック**をシナリオの `expect` として足した
（S72〜S74）。失敗数は突き合わせとは別に数え、終了コードにも効く。
両モード共通の読み書きに関わる修正は、必ず単体テストか絶対チェックで守ること。

絶対チェックの書き方には2つ落とし穴があり、どちらも実際に踏んだ。

- **「行がどこかに在るか」だけを見ると素通りする。** 行の**間に何かが挿し込まれる**欠陥
  （パーサーがコードブロックへ空行を入れる B-2 がまさにこれ）は、各行は在るので通ってしまう。
  `expectLinesIntact` は**連続一致**（`content.includes(lines.join("\n"))`）で見る
- **否定（壊れた形が無いこと）だけを見ると、丸ごと消えた場合を通す。** 「裸のフェンスが無いこと」は
  コードブロックが消滅しても真になる。肯定（正しい形が**在ること**、`expectLinesPresent`）を必ず併せる

また、シナリオの原文と期待する行の並びは**ずれやすい**。連続一致にすると原文の空行まで含めて
書く必要があるので、フィクスチャを変えたら期待も直すこと。
欠陥を再現する形になっているかも確かめる（S74 の字下げブロックは、マーカー風の行を
**2行目以降**に置かないと「マーカーの前に空行を入れる」処理が発火せず、空振りする）。

未解決のまま残す両モード共通の欠陥は `KNOWN_BUGS_BOTH_MODES` に置く
（`KNOWN_BUGS` はモード差の説明に使う枠なので、差の出ないものは載せられない）。

### 巻き戻して落ちることを確かめる手順

修正を1つずつ戻して、守りが本当に効くかを見る。`translator.ts` を丸ごと `git apply -R` すると
新しいテストがコンパイルできない（`protectCodeBlocks` が無い・`restoreCodeBlocks` の戻り値型が違う）ので、
**公開 API の形は保ったまま中身だけ**旧実装に差し替える。

| 巻き戻す対象 | 落ちるもの |
|---|---|
| `protectCodeBlocks` の中身を旧正規表現に | `restore-code-blocks.test.ts` が 12 failing、S73 の絶対チェック、S72・S74 の突き合わせ |
| `parser.ts` の `normalizeMarkerSpacing` のコードブロック除外 | S72・S74 の絶対チェック（連続一致にする前は空振りしていた） |

### 原文が空になったら訳文に触れない（S70）

原文の本文を空にすると訳文が丸ごと空になっていた。原文のユニットが0件になると訳文の全ユニットが
孤立扱いになり、`autoDelete` が本文ごと消すためである。

`sync_CoreProc` に「原文のユニットが0件かつ訳文にユニットがある」ときは訳文に書き込まず中止する段を足した
（ADR-260803-06）。件数は `sourceEmptied` として返り、警告通知を出す。
`unit-state` の末尾行をユニット0件のときは刈らない規則（§10）と同じ考え方である。

決めたこと:

- **判定は parse 直後に置く。** `syncFrontmatterMarkers` は frontmatter オブジェクトを
  その場で書き換えるため、後ろに置くと「中止したのに状態が変わっている」ことになる
- **通知は `syncCommand`（明示実行）と `syncSingleFile`（保存で走る自動同期）の両方から出す。**
  原文を全選択して消す操作はふつう保存で起きるので、自動同期の側で黙ると
  ADR が避けたかった「原文を戻さないまま作業を続ける」状態そのものになる。
  ただし保存のたびに出さないよう、自動同期では**同じ状態が続くあいだ1回だけ**にする
  （ux.md §3.3「変化のたびにトーストを出さない」。通常どおり同期できたら忘れる）
- 通知には孤立ユニット削除の通知と同じ「復旧方法」ボタンを付ける（隣同士で流儀を割らない）

副作用として、**本文が無く frontmatter だけになった原文は以後ずっと同期されなくなる**。
訳文は守られるので害は小さいが、通知文では「原文に本文が無い」と表現し、
作り直したいときは訳文ファイルを消せばよいことを伝えている。

### 直していないもの

- **訳文を手編集しても、編集されたことがどこにも出ない（S71）。** 訳文にコードブロックを
  書き足すとハッシュは正しく更新されるが `need` は付かない。`need` を付けないこと自体は
  **正しい**と考えている。S2（訳文を人手編集しても保持・need なし）と同じ挙動であり、

  ただし**逃げ道として想定していた Decoration も、現状この場面では出ない**。

  「ADR-260801-03 の受け皿に載る」というのは事実ではない。need を足すのか、

  残してある（両モード同じ挙動なので突き合わせでは出ない）

  > 仕様として固定し、この宿題を閉じる。見せてもユーザーに取れる行動が無く（trans は

## 16. 確認待ちの出口を広げた（2026-08-05）

§14(6) の宿題2件を実装した（ADR-260805-01）。

### (a) Keep の恒久化 — 「残す」は独立ユニット化になった

`mdait.unit.keep` の実体を「need を外すだけ」から「**need と from を同時に外して独立ユニットにする**」へ
変えた（`commands/markers/keep-unit.ts`）。独立ユニットは sync のパススルー保護対象
（`sync-command.ts` の independentTargets: hash あり・from なし・need が verify-deletion でない）なので、
次の sync で確認待ちが復活しない。単体テストで「Keep → 原文の章が無いまま sync ×2 → 復活しない・冪等」を固定した。

- need と from を**別々に外せる経路を作らない**。別々に外すと「from なし need:verify-deletion」という
  レガシー形（delete ポリシーで削除される）を再生産する。独立化は必ず `FileHandler.keepUnits` を通す
- `DEFAULT_RESOLVABLE_NEEDS` から verify-deletion を外した。既定の resolve で need だけ消える罠を塞ぐ。
  明示指定（`needs:["verify-deletion"]`）は「一時的に伏せる」操作として残る
- 3接点の対称性: ツリー（`mdait.unit.keep`）・CodeLens（`mdait.codelens.keepUnit`）・
  LM Tool（`mdait_resolve` に `action:"keep"` を新設）がすべて `keepUnits` を通る
- 受け入れた帰結: Keep 後に原文の章が git 等で戻ると、訳文には独立ユニットと新規 translate の
  同じ章が2本並ぶ。独立化は「機械の対応付けから外す」という人の宣言なので、勝手に再連結しない

### (b) ファイル単位の一括確定

確認待ちを含むファイル行（contextValue `mdaitFileTargetVerifyDeletion`）に
「まとめて残す」（`mdait.file.keepVerifyDeletion`）と「まとめて削除」（`mdait.file.deleteVerifyDeletion`）の
インライン操作を付けた。どちらも modal 確認（件数＋章タイトル一覧、15件超は畳む）。
書き換えは `unit-mutation.ts` 経由の一括入口（`keepUnitsAsIndependent` / `deleteAllVerifyDeletionUnits`）で
1回の排他・1回のファイル書き込みで行う。sync 完了通知の「Show units」からツリーへ飛べば一括ボタンに届く。

- 確認の要否は「破壊的か」ではなく「**間違えたとき取り返しがつくか**」で決めた。一括 Keep の誤操作は
  復旧が30回の手作業になるため、削除と同様に modal を掛ける。単体操作は従来どおり（Delete は確認あり・Keep は無し）
- ワークスペース全体の一括は作らない。確認待ちは人が見るための仕組みで、見ずに全部消せる入口は目的と矛盾する。
  複数ファイルにまたがる大改稿が実際に痛くなったら再訪

## 17. 残件の棚卸しと段階1の設計確定（2026-08-06）

外部マーカーの残件を棚卸しし、段階1（孤立訳文の可視化）の未決事項（§8）を全部詰めた。
ロードマップを `docs/roadmaps/roadmap-v01_external-markers.md` に切り出した（段階＝Pxx に対応）。

### 棚卸しで分かった、§8 の前提の誤り

**(1) §5-(1)（frontmatter の gray-matter キャッシュ汚染）は既に直っている。**
`front-matter.ts` は `matter(markdown, {})`（キャッシュ無効）と `structuredClone(parsed.data)` の
両方を持っている。残件から落とす。

**(2) 訳文ディレクトリは、ツリー側では既に列挙されている。**
§8 は「sync は訳文ディレクトリを列挙していない。孤立の検出を載せるなら列挙の新設が要る」と
書いていたが、`status-collector.ts` は `targetDirs` を `collectAllFromDirectory` で列挙している
（`ignoredPatterns` 込み）。**原文の無い訳文はいまでもツリーに出ている。印が無いだけである。**

**(3) sync 側にも列挙の新設は要らない。** 判定材料が2つとも手元にある。

| §8 の3分割 | 何を見れば分かるか |
|---|---|
| (a) 行があるのに実体が無い | `unit-state` の行の `path` に `fs.existsSync` |
| (b) 実体はあるが導出した原文が無い | 同上＋`getSourcePath` の結果に `fs.existsSync` |
| (c) 今回の走査スコープ外 | 既存の `configuredDirs` / `scannedDirs`（§13 で実装済み） |

つまり `cleanupOrphansInScope` の「走査したが見つからなかった → 消す」に
**「ディスクに実在するなら消さない」**を足すだけで済む。

**(4) 訳文側の (a) は、現在まったく検出されていない。**
`sync-command.ts` は導出した訳文パスを**実在確認せずに** `seenPaths` へ入れている。
掃除から見ると訳文の行は常に「見た」扱いになる。

### 決めたこと（ADR-260806-01 / -02）

- **孤立は記録せず、毎回ディスクから計算する。** 判定は「訳文が実在する ∧ 導出した原文が実在しない」の
  一点。7列固定の形式を破らず、`unit-state` を持たない embedded でも同じコードで直る（ux.md の F-10）。
  何も書かないので定常 sync の決定性・冪等性が自明に保たれる。
  **§8 の「孤立行のライフサイクル」は、寿命という概念ごと消えた**（退避ファイルも `.gitignore` への追記も不要）
- **ignore の扱いも自動的に決まる。** ignore された訳文はツリーに出ず、ディスクに実在するので行は残る
  ＝「確かめていないものは消さない」と同じ側に倒れる
- **人が取れる行動は破棄だけ。** 手動再リンクは段階4（判定基準を段階4でまとめて決めるほうが安い）、
  独立化の宣言は段階2完了後に再訪（孤立の発生頻度自体が段階2で大きく下がる）
- **破棄はごみ箱へ移動する。** mdait はこれまでユーザーの文書ファイルを削除したことが無い
  （`unlinkSync` はデバッグ IPC と一時ファイルだけ）。確認の要否と実装を「破壊的か」でなく
  「間違えたとき取り返しがつくか」で決める基準（ADR-260804-01 / -260805-01）に合わせる
- **ツリーは既存のファイル行にその場で印を付ける。** 集約用の仮想ノードは作らない。ツリーが鏡にして
  いるのはファイルシステムなので、仮想ノードは「同じファイルが2箇所に出る」か「本来の場所から消える」
  かのどちらかになる。孤立の典型は原文だけのリネームで、旧訳文と新規の未翻訳訳文が**同じディレクトリに
  並ぶ**ため、その場に出るほうが「こっちが古いほうだ」と分かる
- **通知は新しく孤立したファイルが出たときだけ。** ADR-260803-06 の「同じ状態が続くあいだ1回だけ」と
  同じ形にする。記憶の単位は件数ではなく**パスの集合**（1件解消して1件発生したときに黙らないため）。
  常駐の件数はステータスバーへ
- **エージェントには孤立を見せるが、破棄操作は出さない。** 3接点の対称性（ADR-260805-01）に境界を1つ引く。
  「この訳文はもう要らない」は機械が決めることではない（ux.md「機械が判定できないことを機械が決めない」）

### 実装で分かった、もう1つの落とし穴（sync 後の測り直し）

孤立した訳文は**原文が消えているので sync の処理対象に入らない**（走査は原文ディレクトリを起点にしている）。
つまり `refreshFileStatus` が呼ばれず、ツリーの印は古いままになる。リネームした直後の sync で
孤立が画面に出ないという、気づかせるための仕組みとしては致命的な穴になる。

`refreshOrphanFlags` を sync の最後に置いて測り直す。**ディレクトリの列挙はしない** —
ステータスツリーが既に知っているファイルに実在確認をかけるだけで足りる。印が変わったものだけ
`refreshFileStatus` して、その結果を通知の判断（新しく孤立したものがあるか）にも使う。

### S68 は「空になった側には触らない」の対称化で直す（ADR-260806-02）

原因は貼り戻したときではなく**その手前**にある。`autoSyncOnSave` があるので、全選択して消して保存した
瞬間に sync が走る。そこで訳文のユニットが0件のため原文のユニットが全部「新規」と判定され、行が
`hash=原文コピー / need:translate` に上書きされる。**この時点で元の状態は失われている。**
embedded が戻るのは、貼り戻した本文の中にマーカーが一緒に入っているからである。

ADR-260803-06（原文のユニットが0件なら訳文に触らない）と対称に、訳文のユニットが0件なら
`unit-state` にも書かない。行が無傷なら貼り戻した瞬間にハッシュが一致して**完全復帰**する。
rebuild 検知（`isExternalRebuild`）を広げる案は、着地が「全ユニット `need:review`」で
embedded の完全復帰に届かないため採らなかった。

実運用でより痛い筋書きも同時に守れる: 翻訳会社から戻った訳文で丸ごと差し替える作業は
「全選択 → 削除 → 保存 → 貼り付け → 保存」になりがちで、いまは**この操作をするだけで状態が壊れる**。

### ユニット単位でも同じ壊れ方が起きる（今回は覆わない・roadmap-v01 の P03）

中ほどの章を1つ消して保存すると:

1. `alignEntriesToUnits` は残りを本文ハッシュで正しく結び、**消された章の行はどのユニットにも
   結びつかず返り値から静かに落ちる**（返り値はユニットごとの配列なので、余った行は入る場所が無い）
2. sync が原文からその章を復活させる（原文のコピー＋`need:translate`）。ユニット数は元に戻る
3. `detachMarkers` が order 0〜N-1 を書き直し、**消された章の行があった位置が上書きされる**

保留席（`parkEntriesFrom`）は**末尾の行にしか効かない**。この筋書きではユニット数が戻っているので
`shouldPruneTail(N, N)` は何もせず、保留も刈り取りも起きないまま行だけが消える。ログにも残らない。

貼り戻すと本文は正しい訳に戻るのに行は `need:translate` のまま。`need:translate` は
「✨翻訳が上書きしてよい」の意味なので、**次に翻訳を回すと人の訳が AI 訳で潰される**。

覆うには保留の基準を「末尾の行」から「対応が付かなかった行」へ変える必要があるが、
どの行が対応しなかったかが分かるのは**パース時**で、保留を決めているのは**書き出し時**である。
その間に情報の通り道が無く、配管の新設は `markers-migration` の中間 stringify と embed 経路にも及ぶ。
実質「段階3を今やるか」という問いになるため、roadmap-v01 の P03 として切り出した。
今回は probe にシナリオを足して**モード差として毎回レポートに出す**のと、
いま完全に無言で消えている経路にログを1行足すに留める。

### 段階2の方針（ロードマップ P02）

`onWillRenameFiles` の `waitUntil` に `WorkspaceEdit`（`renameFile`）を返し、原文のリネームに訳文を
連れて動かす。**ユーザーのリネームと同じ取り消し単位に相乗りする**ので Ctrl+Z で両方戻り、
確認は挟まない（＝取り返しがつく側なので、この製品の基準では確認不要）。フォルダごとの移動では
イベント1件でファイルが何十件も動くため、確認を挟む設計はそもそも成立しない。
訳文側をリネームされた場合は原文を動かさず、行の `path` だけ追随させる（原文が正、訳文が従）。
段階1が保険になる — 取りこぼしても孤立として画面に出るので、静かには壊れない。

**落とし穴**: `syncCommand` は毎回 `load()` を無条件に呼んでメモリ上の変更を捨てるため、
リネームのハンドラが `save()` せずに終わると状態が無言で消える。sync 実行中に届いたリネームの保留も要る。

## 18. 移動にペアごと追随する（2026-08-07・段階2 / roadmap-v01 の P02）

段階1で「気づける」ようにした次は「そもそも起こさない」。エディタ上の移動は構造的に潰せる。

### 何が起きていたか

external の行は相手を**パス**で覚えている。リネーム・フォルダ移動でパスが変わると、
その行は誰のものか分からなくなり、掃除で消える（probe S7 / S8 が embedded と差を出していた）。
さらに**原文だけを動かすと**、旧訳文が孤立したうえに新パスへ未翻訳の複製訳文ができる。
こちらはペアがパスから導出されているためで、**embedded でも同じように起きる**（§9）。

### 決めたこと（ADR-260807-01）

- **確認は挟まない。** 訳文の移動は `onWillRenameFiles` の `waitUntil` へ `renameFile` として返す。
  VS Code はこれをユーザーの移動と同じ取り消し単位に入れるので、Ctrl+Z で原文と訳文が一緒に戻る。
  確認の要否を「破壊的か」でなく「間違えたとき取り返しがつくか」で決める基準
  （ADR-260804-01 / -260805-01）では、取り消しに相乗りできる操作は確認不要側に入る。
  加えて**フォルダ移動はイベント1件でファイルが何十件も動く**ため、確認を挟む設計は成立しない
- **原文が正、訳文が従。** 訳文だけが動いたときは原文に手を出さず行の `path` だけ追随させる。
  訳文の位置は原文から導出できるが逆は一意に決まらない（1つの原文が複数言語の訳文を持つ）ので、
  従属の向きを逆にすると1ファイルの移動が他言語の訳文を巻き込む
- **追随は連鎖させる。** `ja→en, en→fr` のピボット構成では、連れて動かした `en/x.md` が
  `fr/x.md` の現役の原文である。`en` で止めると `fr` 側に**新しい孤立を作る**（段階1の
  レビューで見つかった筋書きと同じ構造）
- **行き先が塞がっているときは連れて行かない。** 上書きで移すと別の訳文がごみ箱も経由せず消える。
  連れて行かなかった訳文は原文を失うので、段階1の孤立としてツリーに出る（＝黙って壊れない）

### 行の付け替えは「控え」ではなく「実測」で決める

ファイルを動かせるのは移動の**前**だけ（`waitUntil` に返した編集だけが取り消し単位に入る）で、
行を付け替えてよいのは移動が**成功したあと**である。移動前に行を動かすと、ユーザーが移動を
やめたときに「実体は旧パス・行は新パス」が残り、次の sync で行が掃除されて状態を失う。

最初は前半で立てた計画を控えて後半へ持ち越す実装にしたが、**Ctrl+Z で破れる**。取り消しは
こちらが足した訳文の移動もまとめて巻き戻すが、そのときエディタが何を「移動した」と報せて
くるかは保証が無い。報せに訳文が並ばなければ、控えの署名が合わず訳文の行だけが新パスに
取り残される。

そこで後半は控えを捨て、**そのときのディスクを見て決める**（`planEntryMoves`）。
判定は「訳文がもう新しい場所に居るか」の一点である。

| 状況 | 旧パス | 新パス | 行をどうするか |
|---|---|---|---|
| 連れて動いた | 無 | 有 | 一緒に動かす |
| 連れて行けなかった（行き先が塞がっていた） | 有 | — | そのまま残す |
| 取り消しで巻き戻った | 無 | 有（＝元の場所） | 一緒に戻す |

報せの中身に関わらず、実際に動いたものにだけ行が付いていく。

### ストア単位の排他を新設した（§8 の宿題）

`syncCommand` は入口で `load()` を**無条件に**呼び、出口で `save()` する。その区間に割り込んだ
書き換えは、`load()` が先なら読み捨てられ、`save()` が後なら上書きで消える。どちらも無言である。
`FileMutex` はファイルパス単位なので、この区間は守れない。

`infra/workspace/unit-state-lock.ts` を足し、`syncCommand`・`syncSingleFile`・
`relocateUnitEntries` の3つがストアを読み書きする区間を直列化した。sync 中に届いた移動は
待つだけで失われない — ファイルの移動そのものは VS Code が済ませており、待つのは行の付け替えだけである。

副産物として、明示 sync と `autoSyncOnSave` の単一ファイル同期が重なったとき、
後に `save()` したほうの内容だけが残る競合も閉じた（従来から在ったが誰も守っていなかった）。

### 実測の結果

```
一致 64 / 想定内の差 5 / 未修正の既知欠陥 1 / 想定外の差 0   （probe）
絶対チェックの失敗 0 ／ sweep FAIL=0 ／ npm test 1621件
```

`EXPECTED_DIFF` から4件（S7 / S8 / S10 / S28）が外れ、シナリオを3本足した。

| シナリオ | 変化 |
|---|---|
| S7 原文・訳文を揃えてリネーム | **想定内の差 → 一致** |
| S8 原文・訳文をサブフォルダへ移動 | **想定内の差 → 一致** |
| S10 混合（章挿入＋編集＋リネーム） | **想定内の差 → 一致**（残っていた差はリネームぶんだけだった） |
| S28 章の入れ替え＋サブフォルダへ移動 | **想定内の差 → 一致**（同上） |
| S76 原文だけをエディタでリネーム（新規） | 訳文が連れて動き、孤立も未翻訳の複製もできない |
| S77 原文フォルダごと移動（新規） | 訳文フォルダも連れて動き、入れ子の配下まで追随する |
| S78 行き先の訳文が既にある（新規） | 連れて行かず、旧訳文は訳を保ったまま孤立として残る |

probe は `fs.renameSync` を直接呼んでいたが、S7 / S8 / S10 / S28 と新規3本は
**製品と同じ2つの入口**（`buildRenameFollowEdit` / `completeRenameFollow`）を同じ順序で呼び、
その間に VS Code がやることだけをディスク操作で埋める形にした。S6（原文だけを生の
`fs.renameSync` で動かす）はそのまま残してある — あちらは「VS Code の外で動かされた場合」を
測っており、段階4が受け持つ。

### 覆っていないこと

- **VS Code の外での移動**（git・CLI・外部エクスプローラ）。イベントが来ないので拾えない。
  段階4（内容による再リンク）が受け持つ。P04 の判定基準を決めるには、この取りこぼしが
  実運用でどれくらいの頻度で起きるかの実測が要る
- **移動の最中に届いた保存**。ストアの排他で直列化はされるが、移動と保存が交錯する順序まで
  制御しているわけではない。行は実測で合わせるので、どちらの順でも旧パスに取り残されはしない
- **`withFileMutation` はストアの排他を取っていない。** need の解除・ユニットの削除・Keep も
  「読み込んで書き戻す」区間を持つので、sync と重なれば同じ理由で失われうる（新設した穴ではなく、
  これまで誰も守っていなかった穴である）。塞ぐには各コマンドの入口にも同じ排他を掛けることに
  なるが、区間が深く入れ子になるため再入の確認が別途要る

## 19. ユニット単位の状態喪失を閉じた（2026-08-09・roadmap-v01 の P03）

### 何が起きていたか

訳し終えた訳文から章を1つ消して保存すると、その章の行が **保留も刈り取りもされないまま上書きされ**、
あとで同じ本文を貼り戻しても `need:translate` に固定された（probe S75 / S79）。`need:translate` は
「✨翻訳が上書きしてよい」の意味なので、次に翻訳を回すと**人の訳が AI 訳で潰される**。embedded は
本文のマーカーごと戻るため完全復帰する ＝ external だけが壊れるモード差の欠陥だった。

### 原因は2つあった

**(a) 保留の基準が「末尾の行」だった。**

```
訳文3章・3行（すべて訳し終えて from を持つ）
  ↓ 真ん中の章を消して保存
パース結果は 2ユニット   ← 「行が1つ余った」と分かるのはここだけ
  ↓ sync が原文から消えた章を作り直す
書き出しに渡るのは 3ユニット ← 減ったという事実に一度も触れない
  ↓ detachMarkers が order 0,1,2 をそのまま上書き
消した章の from が消滅。shouldPruneTail も parkEntriesFrom も働かない（数が合っているため）
```

**(b) 対応が付かなかったと分かるのは読み込み時、保留を決めているのは書き出し時で、あいだに
情報の通り道が無かった。** 書き出し時に本文ハッシュで計算し直す手もあるが、翻訳直後は本文が
変わってハッシュも変わるため、生きている行を「対応なし」と誤判定する。読み込み時の照合結果
（`alignEntriesToUnits` の返り値に入らなかった行）をそのまま運ぶ必要がある。

### 変えたこと

**1. 読み込み時の照合結果を書き出しまで運ぶ（`MarkerFileContext.alignment`）**

`attachMarkers` が控えを書き、`detachMarkers` が冒頭で読んで消す。運ぶのは2つだけ。

| 控え | 中身 | 書き出し時の扱い |
|---|---|---|
| `unmatchedOrders` | 対応が付かなかった通常の行の `order` | 上書きされる前に保留席へ移す（`parkEntries`） |
| `recoveredHeldOrders` | 保留席から拾い戻された行の `order` | 席から外す（`dropEntries`）。通常の order で書き直されるため |

行そのものではなく `order` で覚え、使うときにストアから引き直す。控えを取ってから使うまでに
ストアが書き換わりうるため（リネーム追随の `movePath`）、控えの中身を鵜呑みにしない。

ctx を parse と stringify で共有する呼び出しでだけ効く。共有しない呼び出し（markers-migration の
中間 stringify・embed 経路）は控えが空になり、従来どおり末尾を見る判定に落ちる。

**2. 保留席の寿命を無くした（§14(3) の判断を覆した）**

`pruneEntriesFrom` は `order >= units.length` を消していたため、保留席（`HELD_ORDER_BASE` 以降）は
必ず巻き込まれた。上の筋書きだと、預けたその瞬間に消える。

```
保留席へ移す        → 行 0, 1, 2, 1000000
3ユニットぶん書き出す → 行 0, 1, 2, 1000000
刈り取り判定         → 4行に対し3ユニット。1件差なので「怪しい減り方」ではない
                    → order 3 以上を削除 → いま預けた行が消える  ← ここ
```

刈り取りの範囲を `units.length <= order < HELD_ORDER_BASE` に狭めた。席から出るのは
**拾い戻されたとき**（`dropEntries`）と**ファイルそのものを手放したとき**（`removeEntriesByPath`）
だけになった。判定に渡す件数も、席を除いた `countLiveEntriesByPath` に変えている
（席を数に入れると、席がある間ずっと「行がユニットより多い」ことになる）。

**3. 席の拾い戻しを本文ハッシュの完全一致だけに絞った（§14(5) の残存リスクを閉じた）**

席の行は段階1.5（見出しの hash とレベルが両側で一意なら順序を無視して採用）と段階3b でも
拾われていた。席に長く居座らせる以上、弱い手がかりで拾うと「見出しだけ同じ別物の章」に古い
`from` が付き `need:revise@実在しない章` になる。**2 と 3 は対で入れている — 片方だけでは意味を持たない。**

**4. 席へ預けるのは「失うと人の作業が消える行」だけにした**

| 行の形 | 預けるか | 理由 |
|---|---|---|
| `from` があり `need` が空 | **預ける** | 訳し終えた行。失うと人の訳が AI に潰される |
| `need` が `review` / `revise@…` / `isolate` / `verify-deletion` | **預ける** | 人の判断が要る状態 |
| `need:translate` | 預けない | 「まだ人が訳していない」だけ。sync が原文から同じ状態を作り直す |
| `from` も `need` も無い | 預けない | 本文から計算し直せる |
| 本文 hash が空 | 預けない | 完全一致でしか拾わないので、拾い戻す手段が無い |

`need:translate` を外すのが効く。**sync が自分で作り直した訳文の複製**（原文の丸写し）がこの形なので、
預けると席が実際の編集と関係なく増える。加えて**同じ本文ハッシュの席は1つしか持たない**
（同じハッシュの席が2つあっても片方は永遠に使われない。新しいほうで中身を置き換える）。

この2つで、席が増える条件は「**消えたきり戻ってこなかった、内容の異なる章**」だけになる。
同じ章を消して貼り戻すのを繰り返しても1行も増えない（毎回拾い戻されて席が空く）。

### なぜ上限で追い出さなかったか

席に上限を設けて古い順に追い出す案（例: ファイルごとに N 席）は、伸びない代わりに
**「上限を超えたので消えました」という、人から見て理由の分からない失われ方**をもう1つ作る。
いま直そうとしている欠陥とまったく同じ性質のものなので採らなかった。数字に根拠が無い点も含めて、
ADR-260809-01 に記録してある。

拾い戻しが完全一致だけになった以上、居座る行にできることは「1文字も違わない本文が戻ってきたら
その状態を返す」だけで、それ以外の場面では一切効かない。無害な待機である。

### どこまで直ったか（実測）

| シナリオ | 変化 |
|---|---|
| S75 訳したあと**末尾**の章を消して sync → 貼り戻す | **未修正の既知欠陥 → 一致** |
| S79 訳したあと**途中**の章を消して sync → 貼り戻す（新規） | 一致 |

S79 を足したのは、S75 が末尾の章を消す筋書きだったため。末尾を見る刈り取り／保留はそこでは
何も拾えないので、控えを運ぶ経路が働いて初めて守れる。両シナリオとも、控えの適用を外すと
不一致に戻ることを確認してある（＝欠陥をちゃんと捉えている）。

```
npm test              1635件 pass
probe                 一致 66 / 想定内の差 5 / 未修正の既知欠陥 0 / 想定外の差 0 / 絶対チェックの失敗 0
npm run test:explore  FAIL=0 INFO=1（従来からの注記。退行ではない）
```

`KNOWN_BUGS` は空になった。

### 覆っていないこと

- **ctx を共有しない呼び出しは従来どおり。** markers-migration の中間 stringify と embed 経路は
  控えが届かないため、末尾を見る判定に落ちる。移行は両表現を意図的に parse する特殊な経路なので
  現状は据え置いた
- **席の行はツリーにもステータスにも出ない。** 「消した章の状態を預かっている」ことは人からは
  見えず、`.mdait/unit-state` を直接読むか info ログでしか分からない。見せるべきかは
  サーフェス全体の判断（ux.md §3.3）が要るので、ここでは決めていない
- **`delete-unit.ts` の刈り取りは席を巻き込まなくなった。** ユニットを1つ消す操作が、そのファイルの
  席を全部消すことは無くなる。意図的な削除で無関係な席まで掃くのは筋が悪いので、これは意図した変更
