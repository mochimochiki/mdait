## ADR

### ADR-260801-03: 解説は Hover、状態は Decoration、CodeLens は操作だけ — サーフェスの役割分担をデザイン言語として固定する
**背景** : 手入力ユーザー向けの案内を CodeLens に置いたところ、押せるコマンドの列に押せない文章が混ざった。どのサーフェスに何を載せるかの取り決めが無く、置きやすい場所に置いてしまっていた。
**決定** : ux.md §3.3 に「サーフェスの役割分担（デザイン言語）」を新設し UX-P8 として原則化。CodeLens=操作、Decoration=状態を一言、Hover=解説、を不変とする。案内は Decoration（`未完了`）＋ Hover（書き換えただけでは完了にならない旨）へ移し、CodeLens は元の操作だけに戻す。AGENTS.md の Map に ux.md を追加し、UI 変更前の必読とする。
**理由** : 「どこに出すか」を都度考えると必ず置きやすい場所に寄る。載せてよいものを先に決めておけば、判断が設計時ではなくルール参照に落ちる。解説を Hover に集約すると、読まなくても操作できる状態（解説は補助であって前提ではない）が保たれる。
**備考** : 案内は「手作業で編集されたが未確定」のユニットにだけ出す。判定は `MdaitMarker.hasUnconfirmedEdit()`（translate は hash≠from、revise@X は hash≠X）。「訳し終えたか」は機械には判定できないため need の解除は人の宣言のままとし、宣言が必要なことを伝える責任を UI 側が負う。

### ADR-260801-02: 初回導線の行き止まりを塞ぐ（未同期案内のツリー行化・実行前ガード・状態の文字表示）
**背景** : ブラウザ版VS Codeで初級者シナリオを実機通しした結果、sync完了通知の「今すぐ翻訳」が常に失敗、AI不達の理由がログにしか出ない、原文発見だけでWelcomeが消える、docs→docs/enの入れ子でsyncのたび出力が一段深くなる、を確認した。
**決定** : (1)CTAは`mdait.trans.pendingTargets`（翻訳待ちの訳文ルートを対象）に委譲。(2)ディレクトリ翻訳の最初の失敗理由を通知本文に載せ、AI不達なら診断/設定/docsを添える。(3)`validateForRun`を`validate`と分離し同一・入れ子ペアはsync前に停止（doctorのnestedDirsもerrorへ）。(4)未同期時はツリー先頭に「初回同期を実行」行を出す。(5)ユニット行に状態の文字副題を出しrevise専用アイコンを与える。
**理由** : Welcomeはツリーが空のときしか出ないため、案内はツリー行として置くしかない。isConfiguredを厳格化すると「未設定」に落ちて直し方が消えるので、実行前ガードは別関数に分ける。件数だけの結果通知は原因を持たないので、ログを開けない利用者には次の一手が無い。
**備考** : 「手で訳したら翻訳済みにする」は自動判定にしない（訳したか否かは機械には判定できず、確定は人の宣言のままにする）。案内の置き場は当初 CodeLens だったが ADR-260801-03 で Decoration＋Hover へ移した。テンプレート既定は`docs`→`i18n/en`とし、既存サイトのディレクトリ再編を前提にしない。

### ADR-260801-01: 管理下MDのマーカー読取はresolveMarkerIO経由を不変条件化し、external×sync.level 0を非互換としてガード
**背景** : CodeLens・TM・term・保存フック等7箇所が素のparseでマーカーを読み、externalモードでマーカー無し扱いになり静かに誤動作していた。sync.level 0の手動境界もexternalでは表現できない。
**決定** : 管理下MDのparse/マーカー読取は`resolveMarkerIO(ForFile)`経由を必須の不変条件とする（移行処理の両表現parseのみ例外）。externalizeはグローバルsync.level 0でブロック、frontmatter上書きは件数警告＋確認続行、doctorに非互換診断を追加。
**理由** : マーカー保管方式の分岐を各所に書くと必ず取りこぼす。解決点を1つにすればembedded/externalの挙動同一性が構造的に保たれる。非互換組み合わせは入口（externalize/doctor）で見えるのが最も安い。
**備考** : role自動判定の`resolveMarkerIOForFile`を追加。保存フックの初期化判定は`FileHandler.isInitialized`へ委譲。frontmatterのみ使うparseも同経路に統一。

### ADR-260731-03: externalizeのマーカー移送はexternal境界での再parseに揃え、mdait.json書き換えを単一経路化
**背景** : externalizeがembedded parseのorderでstoreへ書くため、サブ境界統合でexternal側のorderとずれ後続ユニットの状態を取り違えた。mdait.json書き換えもタブ再整形でdiffを汚した。
**決定** : externalizeはマーカー除去後の本文をexternal境界で再parseし、(level,title)部分列一致でマーカーを移送してから退避。mdait.json書き換えは`infra/config/config-json-editor`の`setConfigValue`を単一経路とする。
**理由** : storeのorderは「external parseのユニット列」が正であり、書く側がそれに揃えるのが最小修正。設定書き換えの整形保持ロジックは既にsettings-panelにあり、移設して共有する方が再発しない。
**備考** : 移行コマンドは対象数つき確認・キャンセル時もstore保存（消失防止）・件数つき完了通知に統一。サブ境界マーカーがexternalで失われる仕様は不変（確認UIで警告済み）。

### ADR-260731-02: trans.retryLimitは削除でなく配線で閉じる（消費者検出テストの強化が発見）
**背景** : 消費者検出テストをdotted path化した際、`trans.retryLimit`が未配線（translatorはハードコード2）と判明。テンプレート由来で全ユーザー設定に存在するキーだった。
**決定** : 削除でなく配線で閉じる。`TranslatorBuilder`が`config.trans.retryLimit`を`AITranslator`に渡す。
**理由** : 削除すると既存mdait.jsonが一斉に検証エラーになる。文書が約束してきた挙動（既定1・1〜5で調整可）を配線で真にする方が影響が小さい。
**備考** : 既定のリトライ回数は実質2→1に変わる（文書どおりの値に収束）。ADR-260731-01の「削除に倒す」原則の例外で、判断基準は「テンプレート経由で全設定に既在するか」。

### ADR-260731-01: 宣言と実体の整合回収（死に設定削除・既定値正準化・validate人間導線・契約テスト）
**背景** : 全機能調査で、消費者ゼロの設定、既定値の4通り乖離、エージェント専用validateなど「宣言と実体の齟齬」が集中して見つかった。
**決定** : 死に設定`skipCodeBlocks`と用語集JSON死に枝を削除し、既定値はコード実装値へ統一。`mdait.validate`を新設。スキーマ×コード整合とLM Tools契約を単体テストで固定。
**理由** : 約束済みで動かないものは削除に倒し、サーフェス対称性（UX-P1）の穴だけ実装を足すのが最小の整合回収。契約テストが同種の齟齬の再発を構造的に防ぐ。
**備考** : レポート不変条件は「出すコマンドはreport-file経由」へ文言修正。`reports/`のgitignore化はADR-260719-01（履歴はgitに委ねる）と矛盾するため見送り。旧キーが残るmdait.jsonは検証エラーになるため削除が必要。

### ADR-260726-01: Statusから分母判定を分離し、マーカー書き換えとレポート出力を単一経路へ集約する
**背景** : 2週間の機能追加でサーフェスごとに実装が生え、到達不能なツリーアクション・ステータス更新漏れ3件・sync実装の重複・レポート4方式が生じた。
**決定** : 分母判定を`isCountedInProgress`へ分離し`contextValue`から`Status`依存を排除。書き換えは`getFileHandler`、レポートは`shared/report-file`へ集約。sync実処理を1本化。
**理由** : 症状はすべて「集計都合の細工が別の判断へ波及」「サーフェスごとに書き換えを書く」という2つの癖に由来し、経路を1本にすれば構造的に再発しない。
**備考** : マーカー形式は不変。`need:isolate`は据え置き（syncが上書きしないため実害なし）。AIレビューは完了ファイルにも表示。レポートは`.mdait/reports/`。

### ADR-260719-01: CodeLens「その他」メニュー・adoptレポート実ファイル化・レポートの表示言語化
**背景** : 訳文CodeLensの行が長く、原文側isolate宣言UIが無い。adoptレポートは仮想文書でプレビュー不可、文章が英語固定。
**決定** : isolate宣言とnote編集をQuickPick「その他」に集約。adoptレポートを`.mdait/adopt-report.md`の実ファイル化。ラベル注入で表示言語化。
**理由** : 純関数のVS Code非依存とl10n抽出の両立には、ラベル構築だけをUI層に置くのが最小。実ファイルならプレビュー・行リンク・git差分が標準機能で得られる。
**備考** : AIのreason/issuesは`{{responseLang}}`で指示。統計語彙行とnextActionsは英語のまま。TM/用語のプレビューも同様。

### ADR-260712-03: UX-R1（判断サーフェスの完成）を実装しmdait_resolveをaction分岐に拡張する
**背景** : ux.mdのB-1〜B-3（verify-deletionの削除導線欠如・isolate宣言UI皆無・レビュー溜まり時の連続処理手段なし）が未解消だった。
**決定** : 削除導線をKeep/Deleteの2択に分岐、isolate宣言UIとNeeds Attention仮想ノードを追加、`mdait_resolve`に`action`分岐を追加。
**理由** : ツール増殖より確認UI・冪等性の既存インフラ再利用が保守しやすい。人間とエージェントのサーフェスを揃え、マーカー手編集を不要にする。
**備考** : Needs Attentionの集約は`StatusItemTree`（VS Code非依存）に置きテスト可能にした。escalated集約はux.md B-4として見送り。

### ADR-260712-02: needフラグ解決をツール化する（mdait_resolve）
**背景** : need:review / verify-deletion の解決手段が人間のCodeLensのみで、エージェントはhash破損リスクのあるマーカー手編集を強いられていた。
**決定** : LM tool `mdait_resolve`を新設し、CodeLensと同一のコマンド層ロジックでneed除去を実行する。hash/fromは不変。確認UIあり・AI不使用・冪等。
**理由** : 人間とエージェントのサーフェス対称性を確立し、壊れやすいマーカー手編集を正規手順から排除するため。判断の委任境界は変えない。
**備考** : 同時に`mdait_getStatus`の`detail:true`へユニット単位のneed一覧を追加。isolate宣言は範囲外（ADR-260712-03で対応）。

### ADR-260712-01: UX基準ドキュメント docs/ux.md を新設しUX原則を明文化する
**背景** : UXの記述がui.md・design.md・command_*.md・個別ADRに4分割で散在し、ジャーニー全体と課題の全体像を俯瞰する場所がなかった。
**決定** : [docs/ux.md](ux.md)をUXの基準文書として新設し、UX-P1〜P7の原則・人間/エージェントのジャーニー・状態可視化マトリクス・課題台帳・ロードマップを集約する。
**理由** : 横断基準がないまま個別最適を続けると同種の劣化が再発する。原則の明文化で「実行できない操作はサーフェスに出さない」等を機械的に再適用できる。
**備考** : 全数調査で見つけたデッドエンド（ツリーのディレクトリTM commit失敗・引数必須コマンドのパレット露出・英語ダイアログ）は同日修正した。

### ADR-260711-06: AI同期を「既存翻訳の取り込み」ウィザードへ再設計しaiSync語彙を廃止する
**背景** : aiSyncの実利用は既存対訳サイトの初回取り込みに集中しているが、名称と配置が「syncのAI版」という誤解を招き取り込み機能として発見されなかった。
**決定** : `mdait.adopt.run`（既存翻訳の取り込み）と`mdait.aiReview.*`へ改称し、term/tmを任意段に含む統合ウィザード化。互換aliasは設けない。
**理由** : 名前が機能のメンタルモデルを決める。取り込みを主語にした命名・導線が発見可能性を最も上げ、v0.0.1の今なら互換負債ゼロで語彙を揃えられる。
**備考** : 却下: タイトルのみ変更（ID残置）は語彙の恒久乖離を生む。詳細は[command_adopt.md](design/command_adopt.md)。

### ADR-260711-05: 孤立モデルをisolate＋独立ユニットに統合しkeep/backfillを廃止する
**背景** : `need:keep`は素hashと意味的に等価で語彙が冗長、`need:backfill`は原文書き込みという非対称な危険を伴い、実用場面がごく限られていた。
**決定** : keep/backfillを廃止し、keepは素hashの独立ユニット（fromなし・needなし）で代替する。isolateは継承。移行はsyncが決定的に変換する。
**理由** : 「訳文役割の孤立＝fromなし」は構造で自明で、語彙は伝播停止の1ビットだけで足りる。TM除外も包括方式にすれば列挙の更新漏れに依存しない。
**備考** : `orphanTargetPolicy`は delete|verify に縮小。TM commitは「fromあり∧needなし」のみ許可。孤立targetは`need:review`で保護。

### ADR-260711-04: term.detectでソース言語のvariants（表記揺れ）を検出・付与する
**背景** : variantsを消費する側（照合・用語注入・訳揺れ検知）は配線済みだが、唯一の供給源`term.detect`が常に空配列を返していた。
**決定** : 検出プロンプト2種の出力スキーマにsource言語の`variants`を追加し、`sanitizeVariants()`で整形してsource側の`LangTerm`にのみ付与する。
**理由** : 既存のvariantsパイプラインを機能させるには供給源が必要で、検出時に併せて出させるのが追加コールなしで最も自然。ソース中心はCSV列生成仕様と整合する。
**備考** : 照合が大小を区別するため、サニタイズの除外と重複排除は完全一致のみとし大小差は別variantとして残す。`MockTermDetector`は空配列を維持。

### ADR-260711-03: ユニット数上限をtrans.maxUnitsPerRunに一本化し調整困難な設定を廃止する
**背景** : 同じ「1回に扱うユニット数の上限」がaiSyncのreview/alignに別々にあり、transには無かった。閾値系4設定は適切値の判断が難しく露出価値が低かった。
**決定** : 上限を`trans.maxUnitsPerRun`（既定300・0で無制限）に統合しファイル単位で適用する。閾値・ラウンド数の4設定は最適値をコード内定数で固定し廃止する。
**理由** : コスト暴走を防ぐガードは普遍的で、機能ごとに別設定を持つ必然性がない。最適値の定まった微調整値は固定した方が誤設定リスクを避けられる。
**備考** : 超過時の挙動は経路別（trans/reviewはneedを残し次回処理、alignはAI alignをスキップ）。旧キーを書いたmdait.jsonは検証エラーになるため削除が必要。

### ADR-260711-02: mdait.jsonをCustomTextEditorProviderの既定エディタとし表示を切り替える
**背景** : 設定エディタは`mdait.settings.open`経由でしか開けず、mdait.jsonを直接開くと標準JSONエディタが出るため入口の発見可能性が低かった。
**決定** : mdait.jsonにcustomEditorを`priority:"default"`で登録し、既存`SettingsPanel`をbindする。同一タブ内でUI⇔JSONを切り替える。
**理由** : mdait.jsonは常に単一の既知パスで、既存のfs直接読み書きが十分機能していた。「既定エディタとして横取りする」薄い統合なら既存ロジックを変えずに済む。
**備考** : 切替ボタンの`when`は`resourceFilename`判定のため`.mdait/`外の同名ファイルでも表示され得るが、実害は軽微として許容する。

### ADR-260711-01: mdait.json設定エディタとしてWebviewを導入する（P6の例外）
**背景** : mdait.jsonの編集はraw JSONのみで50項目超の全体像が掴めずオンボーディングの障壁だった。VS Code標準の設定GUIはプロジェクトファイルに使えない。
**決定** : `mdait.settings.open`で開くWebviewの設定エディタを追加し、P6（独自UI最小化）の明示的例外とする。UIはスキーマから実行時生成し、検証・IOは拡張側に置く。
**理由** : 階層設定の規模ではTreeView/QuickPickでの発見可能性提供に無理があり、設定画面ライクな一覧・検索が最適。スキーマ駆動でUIとの二重管理を避ける。
**備考** : 書き込みはキー単位の最小差分（順序・インデント保持）。見た目は`--vscode-*`変数でテーマ追従、外部リソースなし・CSPはnonce付きscriptのみ許可。

### ADR-260709-01: AIレビューをバッチ検証化し用語集・TMを双方向マッチで注入する
**背景** : 検証は1ユニット=1コールの直列で、確定済みペアを毎回全件見るauditのコストが高い。用語集・TMが渡らず訳揺れも検知できなかった。
**決定** : `aiSync.review.batchSize`件を1コールにまとめ（index echo・欠落時は部分受理）、用語集とTMを原文/訳文の双方向マッチでper-pair注入する。
**理由** : コール数がbatchSize分の1になりauditの常時再スキャンコストが下がる。訳揺れは片側テキストだけでは判定できないため双方向マッチが要点。
**備考** : batchSize:1は旧ID`aiSync.verifyPairing`の単ペア経路に完全後方互換。用語不整合の判定は決定論lintでなくプロンプトルールでAIに委ねる。

### ADR-260708-01: ユニットnoteをunit-registryに統合しauditはnoteをAIへ渡して判定させる
**背景** : auditは意図的な単文乖離を毎回再報告する（ADR-260706-03の限界）。当初の恒久解「受理台帳」は汎用コメントの誤抑止とstale vouchの穴を抱えていた。
**決定** : `unit-registry`を`hash → {content, note?}`に拡張し、noteは編集時にsyncが旧→新hashへ移送する。auditはnoteをAIに渡す。
**理由** : auditの判定主体はAIなので、人間の意図は「AIへの文脈」として渡すのが最小で一貫する。hashキーで持てばcontent-addressedの自動失効もそのまま享受できる。
**備考** : note編集UIはCodeLens（決定的操作・本文とhashは不変）。人間が書いたnoteはsyncで再構築できないため「状態は文書内」の例外。却下: 受理台帳。

### ADR-260706-03: AIレビュー拡張（対象拡張モード）は確定済みペアを「報告のみ」で監査する
**背景** : auditの対象を`need:review`限定から確定済みペアへ広げるとき、不備を検出したペアに`need:review`を書き戻すかを決める必要があった。
**決定** : `mode:"audit"`を追加し、確定済みペアの不備検出は`flagged`として集計・レポート・hoverに出すだけでマーカーは一切変更しない。pendingの挙動は不変。
**理由** : 原文改訂ドリフトは既にhash-syncが検出済みで、書き戻すと意図的な単文乖離を毎回蒸し返し人間の承認判断を上書きする。受理を記録する語彙が現状ないため。
**備考** : 既知の限界: 意図的な乖離は毎回再報告される（ADR-260708-01のnoteで解消）。詳細は[ai-review](design/command_ai-review.md)。

### ADR-260706-02: 孤立ユニットの統合モデル（isolate導入・判断サーフェス）
**背景** : 訳文孤立はポリシーで削除、原文孤立は表現手段がなく翻訳されると非対称で、ピボット翻訳では役割別に孤立が立つためboolean属性では表せない。
**決定** : 孤立を「ペア（方向）との関係」と捉え、(fromの有無)×(伝播停止フラグ)の2軸で表す。伝播停止の新語彙`need:isolate`を導入し、穴あきは人間へ回す。
**理由** : 必要な新情報は「下流伝播を止めるか」の1ビットだけで、上流孤立は既存のfromなしで表せる。孤立か訳漏れかは人間しか判断できないため機械が決めつけない。
**備考** : ADR-260711-05でkeep/backfillは廃止（isolateは継承）。`need:isolate`はcommit-filterの列挙式除外に必ず追加する。

### ADR-260706-01: AI同期は既存プリミティブを注入合成する薄いオーケストレーターとする
**背景** : `sync(adopt+align) → AIレビュー → レポート`をどう束ねるか、どこまでを新規ロジックにしテストをどの層で担保するかを決める必要があった。
**決定** : `executeAiSync`はsync→ターゲット列挙→レビューを順に呼ぶだけとし、採用・検証・マーカー変異を再実装しない。各段は`AiSyncStages`として注入可能にする。
**理由** : 各段の冪等性・フォールバック・キャンセル再開性がそのまま保たれ、スタブ各段による単体テストが個別機能と同水準で可能になる。
**備考** : 確認UIは冒頭1回（ADR-260705-01）。集計・レポート・nextActionsは純関数に閉じる。v1はワークスペース全体のみでpathスコープは将来課題。

### ADR-260705-03: AIアラインはsync_CoreProcにalignerを注入しmatchResultを再配線する
**背景** : AI審査による対応付け修正を、既存のadopt経路（from確立・need:review付与）を壊さずどこに差し込み、AIServiceをどの層で構築するかを決める必要があった。
**決定** : `sync_CoreProc`のmatch()とupdateSectionHashes()の間でmatchResultを再配線する。alignerはsync時に1回だけ構築して注入する。
**理由** : from書き込み前に再ペア化すれば、既存のfrom確立・need:review・孤立処理・diff検出が無改修で乗る。注入によりスタブAIServiceでの単体テストも可能になる。
**備考** : `syncSingleFile`（autoSyncOnSave）はalignerを渡さないため定常syncは構造的にAI非実行。受理修正が空ならmatchResultを恒等で返す（位置ベースへ復帰）。

### ADR-260705-02: AIアラインは差分審査型としAI同期はプリミティブの合成コマンドとする
**背景** : 既存対訳サイト取り込みの誤対応を根本解決するAIアラインの実現形として、「AIに全面生成させる」案と「機械の結果をAIが審査する」案を比較した。
**決定** : 差分審査型を採る。位置ベースの対応表をAIに渡し`{ok|corrections[]|needBodies[]}`で応答させ、提案は1件ずつ検証して不正のみ棄却する。AI同期は薄い合成とする。
**理由** : 大半のページは構造一致で、審査型は出力サイズと故障モードが問題の数に比例する（全生成型は1個の幻覚で全体が壊れる）。syncの決定性・冪等性とも整合する。
**備考** : AIは`needBodies`で本文を要求できる（上限付き2ラウンド）。この「安いパスで全体→怪しい所だけ深掘り」はレビューのバッチ化にも流用する共有パターン。

### ADR-260705-01: AI利用は明示起動時のみ（定常syncのAI不使用を不変条件化）
**背景** : 全AI経路が確認UIとオンボーディングを通る運用は事実上あったが、「AIがユーザーの明示しないところで動かない」ことが不変条件として明文化されていなかった。
**決定** : 定常sync（autoSyncOnSave含む）はAI不使用・決定的・冪等を維持し、AIを使う処理は必ず明示起動＋確認UIを経由する。AGENTS.mdの不変条件に追記する。
**理由** : syncが「いつ何度実行しても安全・無料・同一結果」であることはエージェントの計画可能性と冪等な再開の基盤で、AIの暗黙起動はコスト・非決定性でこれを壊す。
**備考** : 将来の定期実行系も「ユーザーが明示的にスケジュール設定した」ことを起動要件とする。

### ADR-260704-07: AIペアリング検証のverdict語彙とneed:review自動解除ポリシー
**背景** : adoptの対応付けは位置ベースで、誤対応の安全網が`need:review`の全件人手レビューしかなく、大規模サイトの取り込みでは非現実的だった。
**決定** : verdictを`{match|mismatch|partial|uncertain}`＋confidence＋issues＋reasonに固定。新need語彙は導入しない。
**理由** : 「need:review解除＝人間の承認」の既存セマンティクスをAIが代行する形なら、trans/tm.commit/StatusTreeとの相互作用が既存の枠組みだけで完結する。
**備考** : 自動承認は match ∧ issues空 ∧ 閾値以上 ∧ autoApprove の三重条件のみ（自己申告confidenceは未校正）。新語彙はTM汚染の穴になるため避けた。

### ADR-260704-06: ディレクトリ翻訳をファイル単位セマフォで並列化する
**背景** : design.mdの意図的制約「並列実行: 順次実行」により、数百ファイル規模のサイト翻訳が実用時間で完走しなかった。
**決定** : ディレクトリ翻訳をファイル単位のセマフォ方式（`runWithConcurrency`）で並列化する。同時実行数は`trans.concurrency`（既定3・1〜8）。ユニット単位は行わない。
**理由** : 翻訳の律速はAI応答待ちで、ファイル単位の並列は既存の`FileMutex`にそのまま乗る最小の変更で最大の効果を得る。既定3はCopilotの実用クォータ内。
**備考** : キャンセルは新規着手を止め、実行中ファイルは既存のユニット単位チェックで停止する。ユニット単位並列はマーカー書換の競合リスクに対し利得が薄い。

### ADR-260704-05: backfillを「同一内容プレースホルダ＋即時fromリンク」でモデル化する
**背景** : 訳文側にしかないセクションを原文へ逆翻訳するbackfillで、プレースホルダに`from`逆参照を持たせる案は「from=翻訳元」の既存意味論と衝突した。
**決定** : syncが孤立ターゲットTの本文をそのまま持つ原文側プレースホルダSを生成する。内容同一で`S.hash == T.hash`となり`T.from`設定だけでfromリンクが成立する。
**理由** : 「同一内容→同一ハッシュ」により、backfill待ちの中間状態も含めて全状態が既存のfromマッチング・冪等性の枠組みに乗る。
**備考** : ADR-260711-05でbackfillは廃止した（本ADRは経緯として保持）。

### ADR-260704-04: 用語一貫性検証（term-lint）をcore層の機械照合として実装しmdait_validateで公開する
**背景** : 用語集はプロンプトへのソフトな指示止まりで逸脱の検出・レポート手段がなく、term照合ロジックもcommands層にありVS Code非依存化されていなかった。
**決定** : `src/core/term/`に`term-matcher.ts`と`term-lint.ts`を新設し`mdait_validate`で公開する。読取専用・AI不使用・自動修正なし。
**理由** : AI不使用・読取専用なら翻訳→検証→修正ループ内で何度呼んでもコスト・副作用ゼロで、完成状態を機械判定できる。core移設はMCP/CLI化の布石でもある。
**備考** : 保守的閾値（原文に用語が出現し訳文に期待訳語が全く出現しない場合のみ違反）を採る。偽陽性の多い検証はエージェントに無視されるため。

### ADR-260704-03: 用語集・TMをLM Toolsとして公開しスキップ理由を構造化する
**背景** : サイト全体翻訳では既訳からの知識構築をチャットから駆動する必要がある。またtm.commitはneed残りを黙ってスキップし、理由を診断できなかった。
**決定** : `mdait_term`/`mdait_tm`を既存CoreProcの薄いラップとして新設し、スキップ理由を`classifyTmSkipReason`で分類して案内する。
**理由** : 判断・反復はエージェントに委ね、mdaitは冪等なプリミティブと診断可能な構造化出力を返すのが方針。3つとも2回目が差分0件になる冪等性を既に持つ。
**備考** : `classifyTmSkipReason`と`isTmCommitTarget`の整合は単体テストで固定する。pathはソース/ターゲットどちら側でも受理してスコープ解決する。

### ADR-260704-02: 既存対訳の取り込みをadoptモード＋orphanTargetPolicyで安全化する
**背景** : マーカーなし既訳を管理下に置くと初回syncで`need:translate`が付きtransで既訳が上書きされる。訳文だけのセクションも「意図的に保持」を表現できなかった。
**決定** : adoptモード（syncの引数・永続設定にしない）では、from新規確立時に`need:translate`でなく`need:review`を付与し既訳本文をtrans対象外にする。
**理由** : 誤対応リスクは「必ず`need:review`を経由する」ことで安全網を張り、承認→sync→tm.commitの順序依存はcommit-filterのreview除外で機械的に強制される。
**備考** : 孤立ターゲットは`sync.orphanTargetPolicy`で扱う（`autoDelete`を置換）。`MARKER_REGEX`のneed文字クラスに`-`を追加。

### ADR-260704-01: LM Toolsの出力を共通JSONエンベロープで構造化する
**背景** : エージェントはツール出力から状態を観測して次を計画するが、非構造化テキストではneed一覧・失敗原因・次アクションが機械的に取れなかった。
**決定** : 全LM Toolsが`{schemaVersion, ok, summary, data, nextActions, error?}`のJSONを返す。破壊的変更は一斉更新を伴う。
**理由** : `summary`を必須にすればJSONを解釈しない相手への可読性も保てる。need集計・nextActionsはVS Code非依存の純関数でスキーマを単体テストで検証できる。
**備考** : `nextActions`の生成は「薄いラッパー」原則の明示的例外としてlm-tools層に閉じる。`mdait_translate`はディレクトリ対応で確認UIをスコープ単位1回にした。

### ADR-260629-01: 初心者の落とし穴を「診断コマンド＋エラー導線＋破壊的操作ガード」で予防する
**背景** : primaryLang欠落・向き違い・APIキー直書き・autoDeleteによる訳文消失など、初心者が予測可能な順序で嵌まる落とし穴をコードトレースで再現確認した。
**決定** : 診断core（`runStaticChecks`）をVS Code非依存で分離しIOはプローブ注入、エラーには次アクション導線を付け、`sync.autoDelete`を設定値どおり尊重する。
**理由** : 診断をcoreに置けば各落とし穴を単体テストで「実際に発生させて」検証でき、l10nはUI層に閉じる。エラー導線は既存呼び出しのヘルパー置換で侵襲が小さい。
**備考** : autoDelete是正はドキュメント記載の挙動に実装を合わせるバグ修正でもある。削除前モーダル確認と`sync.level`変更検知は後続課題。

### ADR-260624-01: `.mdait/unit-state`のgit競合をunion merge＋グループ区切りで最小化する
**背景** : externalモードでは全ファイル・全ユニットの状態を単一TSVに集約するため、複数人が別ドキュメントを並行翻訳すると1ファイルへ全員が書き込み競合する。
**決定** : `.mdait/.gitattributes`に`unit-state merge=union`を冪等生成し、`save()`でpath境界に空行アンカーを挿入してファイル単位のブロックを分離する。
**理由** : ローダーが重複行を後勝ちデデュープし`save()`が正準ソートで書き直す自己修復性があるためunion mergeが安全に成立する。真のソースはsyncで再生成できる。
**備考** : スコープは`unit-state`限定（`unit-registry`への適用は将来課題）。`union`はgit組込みドライバでgitconfig不要。

### ADR-260620-01: マーカー外部化を`markers.mode`でlive配線し一括マイグレーションを提供する
**背景** : `UnitStateStore`とparserのexternal経路は揃ったが、実コマンド・UIはembedded前提のままで、保管方式の切替手段と既存文書の変換手段がなかった。
**決定** : グローバル設定`markers.mode`（既定embedded）を追加し、読み書き経路のみ`resolveMarkerIO()`で解決したproviderを通す。一括変換コマンド2種を提供する。
**理由** : モードを1つのグローバル設定に集約すればsource/targetをまたいだ一貫挙動と単純なメンタルモデルを保てる。注入を読み書き経路に限れば回帰面が最小になる。
**備考** : storeキーは全経路でワークスペースルート相対に統一。frontmatterマーカーは両モードともin-file。手動サブ境界マーカーはexternal非対応（ダイアログで警告）。

### ADR-260618-01: 本文ヘッダマーカーの外部ファイル化をオプションとして導入する（足場）
**背景** : マーカーの本文埋め込みはADR-251214-02の中核設計だが、「本文にコメントが残るのが煩わしい」ニーズがあり、後から安全に選択肢を足す余地が必要だった。
**決定** : 保管方式を`MarkerProvider` Strategyとして抽象化し`parse`/`stringify`にオプション注入する。今回は注入点の導入のみ（振る舞い完全不変）。
**理由** : `parse`/`stringify`にexternal分岐を直書きすると密結合が悪化する。Strategy注入なら約20箇所の呼び出し側を変えず既存テストが無改変で通る。
**備考** : 外部ストアは集約TSV1ファイル`.mdait/unit-state`とし、非MDファイルは「ファイル＝単一ユニット」のN=1特殊形として統合する（旧`file-state`は廃止）。

### ADR-260613-02: vscode-lmのsystem prompt送信ロールをAssistantからUserに変更する
**背景** : VS Code LM APIはsystemロール非対応のためsystem promptをAssistantとして先頭送信していたが、指示を「自身の過去の発話」として読ませる形は意味論上不適切。
**決定** : system promptを先頭の`User`メッセージとして送信する。`modelOptions`は標準化されたキャッシュ制御が存在しないため空のまま維持する。
**理由** : Userロールなら指示として自然に解釈される。出力に影響しうるため単独の変更とし、問題があれば1行で戻せるようにした。

### ADR-260613-01: プロンプトをsystem / user-sectionに分割しプレフィックスキャッシュを有効化する
**背景** : 可変データをsystem promptの中間に埋め込む構造のためユニットごとに全体が変わり、OpenAI・Ollama・Copilotのキャッシュが一切効いていなかった。
**決定** : テンプレート内マーカー`<!-- mdait:user-section -->`で分割し、前半（完全静的な指示）をsystem、後半（可変ブロック＋本文）をuser messageとして送る。
**理由** : system部がプロンプト種別ごとの単一プレフィックスになり、言語ペア・翻訳方向をまたいでキャッシュが共有される。代償はuser側に増える数行だけ。
**備考** : マーカーのないテンプレートはレガシーモードで従来挙動を完全維持。OpenAIには`prompt_cache_key`を付与しusageをai-stats.logに記録して効果を実測する。

### ADR-260531-02: パス相対化をドライブレター非依存にしコマンド失敗をLogger表出する
**背景** : IPCの大文字`C:`とVS Codeの小文字`c:`の差で`startsWith`相対化が一致せず`tm.commit`が失敗し、失敗もログに出なかった。
**決定** : パス相対化を`path.relative`ベースに置換し、`tm.commit`/`term.detect`/`term.expand`の握り潰しを`Logger.error/warn`に統一する。
**理由** : `startsWith`前方一致はドライブレター大小と区切り境界に脆弱で、`path.relative`はOS規約に従い堅牢。失敗をログに出せば異常を機械検出できる。
**備考** : 兄弟ディレクトリ誤一致（`/ws/ja`→`/ws/ja-backup`）も同時に解消。term系の検出件数が機械可読でない点はフォローアップ課題。

### ADR-260531-01: ステータス同期ズレ観測をfire履歴タイムライン方式で行う
**背景** : 「コマンドは成功するがUIが同期されない」事象を前後の状態スナップショット差分だけでは見逃す。観測のために本番のfire経路を改変するのは厳禁だった。
**決定** : `fire()`の各箇所に`DebugFireRecorder.record()`を挟みseq付きで記録する。recorderは`enable()`まで全操作no-op。
**理由** : タイムラインがあれば最終状態では消える中間挙動を時系列で復元でき、「状態は変わったのに個別fireが飛んでいない」ギャップを機械検出できる。
**備考** : 却下: スナップショット差分のみ（中間の取りこぼしを観測できない）、VS Codeイベントの外側傍受（発火元の引数が取れず粒度が落ちる）。

### ADR-260421-02: FileExplorerのパス解決基準を動的ゲッターにする
**背景** : `workspaceRoot`がコンストラクタで固定され、後からカスタムコンフィグパスを設定しても解決基準が変わらなかった。引数なし呼び出しが多数あった。
**決定** : `workspaceRoot`をプライベートゲッター`configBaseDir`に変え、毎回`getConfigBaseDir()`で動的に解決する。
**理由** : `FileExplorer`はステートレスなユーティリティで毎回の呼び出しは軽量。シグネチャを変えずに全呼び出し箇所へ反映でき、循環依存も生じない。
**備考** : 却下: コンストラクタに`configBaseDir?`を追加（多数の`new FileExplorer()`を全て修正する必要がある）。

### ADR-260421-01: カスタムコンフィグパスの注入方式 — initialize(customPath?)を採用
**背景** : モノレポ対応でユーザー指定のコンフィグパスを`Configuration`に渡す必要が生じたが、`Configuration`は`ExtensionContext`を持たない設計だった。
**決定** : `Configuration.initialize(customPath?)`にオプション引数を追加し、`extension.ts`が`workspaceState`から取り出して渡す。

**備考** : 却下: `setConfigFilePath()`追加（エントリポイントが2つになる）、`getInstance(context)`変更（全呼び出し箇所への波及が大きい）。

### ADR-260404-01: infra層新設とservices層の見送り
**背景** : src/直下にconfig・utils・debug・llmが散在し新ファイルの配置基準が不明確だった。レイヤー浄化の議論でservices層とinfra層の両方が候補に上がった。
**決定** : infra層を新設しconfig/llm/utils/debugを統合する。services層は導入しない。`lm-tools/`と`prompts/`はトップレベルに据え置く。
**理由** : services候補は4つで性質がバラバラ（戦略・データ収集・定数・ユーティリティ）で統一基準が定義できない。育った時点で切り出す方が受け皿化を防げる。
**備考** : `lm-tools/`はcommandsと並列のエントリポイント層で、commands配下に入れると呼び出し側/呼ばれる側が混在する。

### ADR-260329-04: FileHandler Strategyによる多フォーマット翻訳対応
**背景** : 非MDファイル対応にあたり、sync・trans・status-collector・extension.tsの4箇所にMD/非MD分岐が散在する問題がスパイクで判明した。

### ADR-260329-03: vscode依存の切り離し方針 — 値DI + 関数DI
**背景** : 単体テストで実行不可だった原因は、ロジックが`Configuration.getInstance()`等を内部で呼びロード時にvscodeが読まれることだった。

**理由** : Configオブジェクトごと渡すと型依存が残りモックが必要になるが、値だけならテストは単純なリテラルで済む。関数型を使い過度な抽象化も避けた。

### ADR-260329-02: テスト層の3層分類とunit対象の切り分け基準
**背景** : `test:unit`はcore/**のみ対象だったが、commands/**の大半もVS Code非依存で常時実行できた。ただしglobで含めるとvscode解決に失敗するファイルが混在した。

### ADR-260329-01: パッチ形式を`=`/`-`/`+`プレフィックスに統一する
**背景** : unified diff風の形式では、Markdownのリスト項目（`- item`）や水平線（`---`）が削除プレフィックス`-`と衝突しパーサーが正しく分類できなかった。
**決定** : コンテキスト行のプレフィックスを`=`とし、全行が`=`/`-`/`+`のいずれかで始まる形式に統一する。unified diff互換とフォールバック実装は削除する。
**理由** : Markdownで`=`から始まる行は実質存在せず衝突リスクがゼロ。LLMにも「全行が3文字のいずれかで始まる」ルールが明快でミス率が低い。
**備考** : 却下: スペースプレフィックス（インデントとの混同・LLMが忘れやすい）、heuristicフォールバック（複雑で偽陽性リスク）。

### ADR-260328-02: patchMode失敗時にサイレントフォールバックではなくユーザー確認を挟む
**背景** : パッチ形式の揺れで失敗すると警告ログのみで全文再翻訳にフォールバックしていた。全文再翻訳はユーザーの手修正を完全に上書きしデータ損失に直結する。
**決定** : パッチ適用失敗時に警告ダイアログを出し、「スキップ」を選べば既存翻訳を保持してマーカー更新もスキップする。あわせて`@@`ハンク行の自動補完を追加する。
**理由** : 手修正はユーザーの知的作業の成果で、機械的なフォールバックで無言に消すのは避けるべき。補完で成功率を上げつつ最終防衛線に人間の判断を置く二段構えとした。
**備考** : 却下: 全文再翻訳前のバックアップ作成（ファイル管理が複雑化し、気付かないまま上書きが進む可能性が残る）。

### ADR-260328-01: debug-ipcの結果報告に部分失敗ステータスと構造化ログを導入する
**背景** : result.jsonの`status`が2値のため、syncが部分的にファイルエラーを起こしても`done`で返りエージェントが成功と誤判断した。ログもパースが必要だった。
**決定** : `status`に`done-with-errors`を追加し`errorCount > 0`のとき設定する。構造化ログ`structuredLogs`も文字列ログと併存させる。
**理由** : 自律テストでは3値判定で分岐が書ける方が、全ログをパースして失敗を検出するより簡潔で堅牢。構造化ログは既存ログを壊さず追加でき後方互換を保てる。

### ADR-260322-01: TM検索クエリを行単位分割し既存APIを無変更で再利用する
**背景** : TMエントリは文単位なのに検索クエリはユニット全体テキストで、長いユニットでJaccard類似度が希薄化していた。行単位化とP8原則の整合が課題だった。
**決定** : `tm-line-search.ts`をcore/tm/に新設し、内部で正規化→行分割→各行を既存の検索APIに渡す。既存APIは一切変更しない。
**理由** : `normalizeForTm`は正規化済みテキストに再適用しても不変（べき等）なため、二重正規化の実害がなく`preNormalized`フラグや新メソッドの追加が不要。
**備考** : 守ること: 外部呼び出し元は生テキストを渡す（P8）。各行で正規化が重複実行されるため、行数が極端に多い場合は軽微なオーバーヘッドがある。

### ADR-260320-02: TM normalize処理をモジュール内部に閉じ込める
**背景** : `stripMarkdown`がtrans-command・TmxStore・tm-rankerの3層に散らばり同一テキストに最大3回実行されていた。「誰が正規化するか」が不明確だった。
**決定** : 正規化は必要とするモジュール（`TmxStore`・`tm-ranker`）の内部実装に閉じ込める。呼び出し側は生テキストを渡すだけとし、事前の`stripMarkdown`は禁止する。
**理由** : 二重適用を構造的に防ぐには、正規化の発動権を「使う側」ではなく「そのデータを管理する側」に持たせるのが最も単純。
**備考** : 守ること: 呼び出し側は常に生テキストを渡す（`commit-processor.ts`のLLMプロンプト用途は対象外）。trigramキャッシュも`TmxStore`が保持する。

### ADR-260320-01: TM retrieval = trigram転置インデックス + Jaccard + MMR の2段パイプライン
**背景** : exact matchのみでは原文が少し変わるとTM参照がほぼゼロになる。初期実装ではtrigramインデックスがprimaryのみでja→en方向がほぼヒットしない重大バグもあった。
**決定** : 粗い絞り込みにtrigram転置インデックス（lang別分離）、精密スコアリングにJaccard類似度（純関数）、候補の多様性確保にMMRを使う2段構成とする。
**理由** : exact matchから脱却するとdiff-awareな文改訂でもTMが活用できる。embeddingはオフライン不可・外部APIコスト増のため、まず説明可能なlexical中心で構成する。
**備考** : 守ること: インデックスはlang別に分離して構築する（初期バグの再発防止）。embeddingによるrerank層の後段追加は未検討。

### ADR-260315-03: TM commitのguarded upsertアーキテクチャ
**背景** : tm-commitがpair相対の対称設計を残していたため、multi-hop commitで既存primary sentenceを再利用できず同一概念が別TUに分裂していた。
**決定** : Command層でprimaryUnit/localUnitを先に確定し、processorはguarded upsertに専念する。LLM応答はfail-closedで処理する。
**理由** : 正本一意性を保証するにはCommand層で入力を正規化してからprocessorに渡す二段構えが必要。fail-closedならTMXの整合性破壊を構造的に防げる。
**備考** : 守ること: `reuse`行は既存TUへ、`create`行のみ新規TU候補とする。却下: fail-open（不正でも書き込む）はTMX整合性を保証できない。

### ADR-260315-02: TM正本管理をprimaryLang基準のtuid一意性に統一
**背景** : 初期設計はsource/target対称（翻訳方向相対）だったため、多段翻訳（ja→en→zh）で同一概念が別TUに分裂し、同一primary sentenceが複数tuidを持った。
**決定** : `primaryLang`をトップレベル設定とし、TM正本を`primaryLang`のsentence、`tuid = hash(norm(sentence))`を唯一の保存キーとする。
**理由** : source-relative設計ではnon-primary言語からのcommit時にTU一意性が保証できない。`x-unit-path`ベースのキーよりsentence hashの方が意味的に正確。
**備考** : 守ること: `primaryLang`は必須設定（未設定はvalidation error）。旧TMXはtuidからprimaryを逆引き復元する互換読み込みを維持する。

### ADR-260315-01: TMX保存から補助propをYAGNIで廃止
**背景** : `x-primary`・`x-source-hash`・`x-unit`等の補助propを保存していたが、正確に更新し続けるコストに見合う有用なユースケースが見つからなかった。
**決定** : TMX保存契約は`tuid + tuv（各言語variant）+ tuv provenance`を正本とし、補助propは新規保存から除去する。旧TMXの互換読み込みのみ維持する。
**理由** : 「あると便利そう」だけでは正確に保てないフィールドを持ち続けるコストは正当化できない。cleanupはtuidベースの原文現存確認で実現できる。

### ADR-260209-01: 文分割をIntl.Segmenterベースに変更
**背景** : 正規表現ベースの文分割は日英中の混合文・省略語（Dr., etc.）・括弧内の文末記号で誤分割が発生し、TM参照の品質を下げていた。
**決定** : `Intl.Segmenter({granularity: "sentence"})`を採用し言語ごとにキャッシュする。コードブロック保護と段落・リスト独立分割は既存ロジックを維持し公開APIも不変。
**理由** : Node.js 18+でサポート済みのネイティブAPIで、ICUベースなら多言語の文境界を適切に検出でき正規表現よりメンテナンスコストが低い。
**備考** : 守ること: コードブロック内の文分割は禁止。却下: 正規表現のカスタム拡張（省略語・混合言語の例外処理が無限に増える）。

### ADR-260208-01: stripMarkdownで構造（見出し・段落区切り）を保持する
**背景** : TM登録・検索時の正規化で見出しと本文が連結され（「結論 AI技術の進化…」）LLMの文脈理解を損なっていた。正規表現ではネスト構造の検出が困難だった。
**決定** : markdown-itのトークンツリー走査でトップレベル要素の境界を`\n\n`、リスト項目・表セルを`\n`で保持する。インラインコードはバッククォート付きで残す。
**理由** : markdown-itは既存依存で追加コストなし。インラインコード保持でコードを含む文のTM検索精度が上がる。frontmatterは誤認識しやすく手動照合が安全。
**備考** : 守ること: frontmatterは先頭パターンマッチで除去する（markdown-itに依存しない）。

### ADR-260201-01: ロギング基盤をOutputChannel唯一出口 + Loggerクラスに集約
**背景** : `console.log`が各所に散在し、ログレベル制御・フォーマット統一・ユーザー通知との分離ができていなかった。出力チャネルが複数に分岐するリスクもあった。
**決定** : `OutputChannel`を唯一の正式ログ出口とし`Logger`シングルトンに集約する。ユーザー通知とは完全分離し、ログメッセージは英語で統一する。
**理由** : 出力が散らばるとデバッグ時の問題特定が困難。通知とログを同一経路にすると、ユーザーに見せるべきでない内部情報が漏れるリスクがある。
**備考** : 守ること: `console.log`の直接使用禁止（Logger経由のみ）。`AIStatsLogger`のみコスト追跡目的の別系統として独立維持する。

### ADR-260131-01: UnitRegistryをバケット化・決定的出力に変更
**背景** : 原文スナップショットを単一フラットファイルで管理していたためgit merge競合が頻発した。部分追記方式は順序不定でgit diffがノイズになった。
**決定** : CRC32の先頭3桁で4096バケットに分割し、常にバケット昇順・エントリ昇順で全体を書き直す（partial append廃止）。同一入力から常に同一出力とする。
**理由** : 決定的な全書き直しなら同一状態のファイルはgit diffがゼロになりマージ競合が解消される。バケットヘッダも有効なCRC32形式に統一しパースを単一化する。
**備考** : 却下: DB/SQLiteへの移行（配布・インストールが複雑化。ファイルベースの方がgit管理と相性が良い）。5MB超過時はGCを実行する。

### ADR-260124-01: conflict概念を廃止しneed:reviseに統一
**背景** : 翻訳では原文と訳文の同時変更は日常的で、これをconflictとして人手介入を要求するのは過剰防衛だった。解決UIの複雑性のみが残っていた。
**決定** : `need:solve-conflict`を廃止し、source変更時は常に`need:revise@{oldhash}`に統一する。hashは常に最新値へ更新する。
**理由** : LLMには差分と変更後訳文の両方が渡るため、並走変更は自動改訂（diff-aware revise）で自然に吸収できる。解決UIは複雑な割にLLMで代替可能。
**備考** : 守ること: target-only変更（訳文の直接編集）は`need:revise`にしない。差分過大・構造破壊など真に危険な状態への対応は将来検討。

### ADR-260112-01: TranslationCheckerをmarkdown-it構造比較に変更
**背景** : 正規表現ベースの品質チェックは精度が低く（順序考慮なし・ネスト未対応）、見出し・リンク・画像などの構造チェックも欠けていた。
**決定** : markdown-itでパースした構造（見出しレベル別数・リスト・コードブロック・引用・表・リンク・画像）を原文と訳文で比較し、不一致を具体的に報告する。
**理由** : 正規表現ではネスト構造の正確な検出が困難で追加コストが高い。markdown-itは既存依存で追加コストなく、トークンツリーから構造を正確に抽出できる。

### ADR-260111-01: AIServiceインターフェースをPromise\<string\>に統一
**背景** : 初期実装はストリーミング応答（`AsyncIterable<string>`）を返していたが、全コマンドが結局バッファリングしてから処理しUX上のメリットが皆無だった。
**決定** : `sendMessage()`の戻り値を`Promise<string>`に統一し、バッファリングはプロバイダー責務とする。
**理由** : 全コマンドがバッファリングしている以上、インターフェースだけストリーミングにしても複雑性しか残らない。必要になれば別メソッドを追加すればよい。

### ADR-260110-01: OpenAI API呼び出しでstore:falseをハードコーディング
**背景** : 翻訳対象は機密文書を含む可能性があり、プロンプト・応答のサーバー保存が許容できないケースがある。設定可能にすると設定ミスで漏洩するリスクが生じる。
**決定** : `store: false`を常にハードコーディングし設定で変更不可とする。APIキーは`${env:VARIABLE_NAME}`形式で環境変数から読み込む（平文保存禁止）。
**理由** : 翻訳ツールの性質上、機密性は非交渉的な要件。「設定で変更できる」という選択肢自体がセキュリティリスクになるため構造的に排除する。
**備考** : OpenAIのデバッグログ・活用分析は利用不可（受け入れるトレードオフ）。

### ADR-260103-01: プロンプトの外部ファイルオーバーライド機構を導入
**背景** : デフォルトプロンプトが全ユーザーに固定されていると専門ドメイン・特定スタイルへの最適化が不可能で、翻訳品質はプロンプトに大きく依存する。
**決定** : `mdait.json`の`prompts`で任意のプロンプトIDにファイルパスを指定して上書きできる。変数展開は`{{variable}}`形式。ファイル不在時は警告ログを出す。
**理由** : プロンプトIDをコードの識別子として固定しテキストを外部化すれば、コード変更なしにカスタマイズできる。サイレントフォールバック禁止はパスミスの見逃しを防ぐ。
**備考** : 守ること: プロンプトIDはコード識別子として安定させる（リネーム禁止に準ずる）。却下: 全文をmdait.jsonに直接記述（エスケープが煩雑）。

### ADR-251214-02: 管理情報をドキュメント内HTMLコメントに埋め込む
**背景** : 外部ファイル（TSV・サイドカー）に管理情報を分離すると、ファイルのコピー・移動時に整合性が崩れる。埋め込む場合はレンダリング時の干渉を防ぐ必要がある。
**決定** : hash・need・fromを`<!-- mdait {hash} [from:{hash}] [need:{flag}] -->`形式のHTMLコメントで埋め込む。形式とCRC32は変更禁止。
**理由** : ファイル単体で自己完結するため移動・コピーで管理情報が失われず、バージョン管理と相性が良い。どんな状態からでも`sync`で復帰できる冪等性も保証できる。
**備考** : 守ること: マーカー形式は変更禁止。却下: サイドカーファイル（`file.ja.md.mdait`）はファイル移動時に管理情報が孤立する。

### ADR-251214-01: ハッシュアルゴリズムにCRC32を選択（SHA-256ではなく）
**背景** : マーカーにハッシュを埋め込むためハッシュ長がMarkdownの可読性に直接影響する。用途はセキュリティではなく「テキスト変更検出」である。
**決定** : CRC32（8文字）を採用しSHA-256（64文字）は不採用とする。ハッシュアルゴリズムは後方互換性のため変更禁止とする。
**理由** : SHA-256は64文字でマーカーを視覚的に壊す。数千ユニット規模の衝突確率はCRC32でも実用上無視でき、暗号強度は不要。
**備考** : 守ること: CRC32固定。衝突時は`sync`で再ハッシュされるため運用上問題ない。
