# Adopt — 既存の対訳サイトを mdait 管理下に取り込む

すでに原文・訳文の両方が存在するサイト（マーカーなしの既訳）を、既訳を壊さずに mdait 管理下へ置くための手順です。

## いつ使うか

- 手翻訳や別ツールで作った日英ページがすでに揃っているサイトを mdait に移行するとき
- 訳文ファイルに本文はあるが mdait マーカーがないとき

このまま通常の `mdait.sync` を実行すると、既訳ユニットに `need:translate` が付き、次の翻訳実行で **既訳が AI 翻訳に上書きされます**。adopt はこれを防ぎます。

## 手順

1. **git にコミットする（必須推奨）**。取り込みはマーカー書き込みを伴うため、いつでも戻れる状態にしておきます。
2. `.mdait/mdait.json` の `transPairs` を設定します。訳文側に独自セクションがあるサイトでは、先に `sync.orphanTargetPolicy` を `"verify"` または `"keep"` にしておくと安全です（デフォルトの `"delete"` は独自セクションを削除します）。
3. **adopt モードで sync を実行**します。Copilot Chat から `mdait_sync` ツールに `adopt: true` を渡すか、エージェントに「adopt で取り込んで」と依頼します。
4. 結果を確認します:
   - 原文と対応が取れた既訳ユニット → `from` が確立し **`need:review`** が付きます（本文は1文字も変わりません）
   - 原文側にしかないユニット → 通常どおり `need:translate` の空ユニットが訳文側に生成されます
   - 訳文側にしかないユニット（孤立ターゲット） → `orphanTargetPolicy` に従って処理されます
5. **`need:review` ユニットをレビュー**します。順序ベースの対応付けが正しいか（原文と訳文の見出しがズレてペアになっていないか）を重点的に確認します。ユニット数が多い場合は **AIペアリング検証**（StatusTree の「AI Review」または Copilot Chat の `mdait_aiReview`）でトリアージできます — 高確信で一致と判定されたユニットは `need:review` が自動解除され、不一致・翻訳漏れの疑いがあるユニットだけがレビュー対象として残ります（自動承認の閾値・有効/無効は `aiSync.review` 設定で制御）。
6. 問題なければマーカーの `need:review` 部分だけを削除して承認します（`hash` / `from` は変更しないこと）。レビュー承認の判断はエージェントに委任することもできます。
7. `mdait.sync` を再実行して状態を確定し、`tm.commit` で既訳を翻訳メモリに登録します（`need` が残っているユニットは TM 登録対象外のため、レビュー解消が先です）。

## need フラグの流れ

```
マーカーなし既訳
  └─ sync (adopt) ──→ from確立 + need:review（既訳は不変・transも触らない）
        └─ 人間/エージェントのレビュー ──→ need除去
              └─ sync ──→ 翻訳済み（定常状態）
                    └─ tm.commit ──→ TM登録
```

## 誤対応（mismatch）が見つかったときの復旧

位置ベースの対応付けがズレて誤った `from` リンクが書かれた場合（章の欠落・追加・順序入れ替えのあるファイル）、次回以降の sync は `from` リンクを優先して維持するため、放置しても自然には直りません。`need:review` が残る限り翻訳や TM への流出はないので、既訳が壊れることはありませんが、リンクの修復は以下の手順で行います:

1. 誤ペアと判定された（AIペアリング検証で mismatch の）訳文側ユニットの mdait マーカー行（`<!-- mdait ... -->`）を削除してリンクを解除します
2. 章の順序が原文とズレている場合は、訳文側のセクションを原文の順序に合わせて並べ替えます（欠落章は何もしなくてよい — 再 sync が正しい位置に `need:translate` の空ユニットを生成します）
3. 再度 adopt モードで sync を実行します。正しく対応済みのユニットの `from` リンクはアンカーとして機能し、マーカーを外したユニットだけがアンカー間の区間内で再対応付けされます
4. 再度 AIペアリング検証を実行して結果を確認します

## backfill の使いどころ

訳文側にしかないセクションを原文側にも持ちたい場合は `orphanTargetPolicy: "backfill"` を使います。sync が原文側にプレースホルダ（`need:backfill`）を挿入し、次の翻訳実行が言語を逆転して原文言語へ翻訳・埋め戻します。生成された原文ユニットには `need:review` が残るので、内容確認後にフラグを外してください。原文ファイルへの書き込みを伴うため、取り込み前の git コミットを推奨します。

## keep の使いどころ

訳文側にしか存在しないセクション（例: 英語版限定の案内）は `orphanTargetPolicy: "keep"` で `need:keep` を付けて恒久保持できます。

- `need:keep` ユニットは sync の対応付け・削除の対象外、trans の翻訳対象外になります
- ステータス上は「独自ユニット」として翻訳率の分母から除外されます
- 個別に保持をやめる場合はユニットごと削除するか、`need:keep` を外して次の sync のポリシー判断に委ねます

## 注意事項

- adopt は **取り込み時に一度だけ使う操作**です。定常運用の sync では指定しないでください（`adopt` は sync の引数であり、設定ファイルには保存されません）。
- 対応付けは見出しの順序ベースです。原文と訳文で見出しの数や順序が大きくズレているファイルでは誤対応が起こりえます。誤対応も `need:review` のレビューで検出できますが、ズレの大きいファイルは取り込み前に構造を揃えておくと確実です。**サイトの状態パターン別に何が起きるか・どの仕組みが守るかの網羅一覧は [command_ai-sync.md の取り込みパターン網羅マトリクス](../../design/command_ai-sync.md)を参照してください。**
- マーカー保管方式が `external` の場合、unit-state が存在しないファイルは rebuild 安全網により自動的に同じ動作（既訳を `need:review` に倒す）になります。
