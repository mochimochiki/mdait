# mdaitアーキテクチャ：設計哲学

## mdaitの存在理由

翻訳は一度きりの行為ではない。現実の翻訳運用は、原文の継続的な更新、用語の統一、複数言語間の同期という、動的で複雑なフローである。

従来の翻訳ツールは「文書全体を一度翻訳する」ことに最適化されており、**差分翻訳の運用課題**を解決していない：

- どこが変わったのか、どこを再翻訳すべきか、人間の目視に依存する
- 用語集を用意しても、実際の翻訳時に確実に反映される保証がない
- 翻訳後の手修正が無駄になる（原文変更で全文再翻訳されてしまう）
- Gitのdiffでは文書構造を理解できず、マークダウンの段落変更を正確に追跡できない

mdaitは、「**継続的な多言語文書管理**」を実現するために存在する。一回きりの翻訳ではなく、文書が生きている限り続く翻訳運用を、構造的に支えるツールである。

## 設計哲学の核心

### 1. 管理情報は文書内に完結させる

mdaitの管理情報（マーカー）はMarkdown文書内にHTMLコメントとして埋め込まれる。外部データベースも管理ファイルも不要。

**理由：**
- 文書と管理情報が分離すると、コピー・移動・リネーム時に整合性が崩れる
- gitでバージョン管理する文書の管理情報は、文書自体と同じバージョン管理下にあるべき
- 文書を見れば状態がわかる。ツールに依存しない透明性

**トレードオフの受容：**
文書にマーカーが挿入されることは、Markdownの純粋性を損なう。しかし、HTMLコメントはレンダリング時に不可視であり、可読性への影響は最小限である。この小さな代償と引き換えに、ツール依存を劇的に下げ、長期運用の安定性を得る。

### 2. ハッシュによる変更追跡

mdaitはCRC32ハッシュで各ユニットの内容を追跡する。gitのコミット履歴ではなく、**文書そのものの内容**で差分を検出する。

**理由：**
- git履歴に依存すると、コミット粒度や履歴が壊れた時に翻訳管理が破綻する
- ハッシュベースの追跡は、どんなVCS（またはVCS未使用環境）でも動作する
- ユニット単位の内容変更を決定的に検出できる

**選択：**
暗号学的に強いハッシュ（SHA-256等）ではなくCRC32を採用。衝突リスクより、短いハッシュによる可読性とファイルサイズを優先。実運用での衝突確率は極めて低い。

### 3. 翻訳ドメインにおける「conflict」の否定

mdaitは、原文と訳文の両方が変更された状況を「conflict」として扱わない。すべて`revise`（改訂）として処理する。

**理由：**
翻訳ドメインでは、原文が変わりながら訳文も手修正されることは**通常のワークフロー**である。これをconflictと呼び、手動マージを強制するのは過剰防衛であり、運用を阻害する。

代わりにmdaitは、LLMによる**diff-aware revise**を主戦力とする。原文の変更差分（unified diff）と前回訳文をLLMに提示し、訳文への差分パッチを生成させる。これにより、変更箇所以外は既存訳文を維持し、人間の修正を尊重する。

### 4. 冪等性と決定性

すべてのコマンドは何度実行しても安全で一貫した結果を返す。`sync`を10回実行しても、状態は同じである。

**理由：**
- 翻訳運用は複数人、複数タイミングで実行される
- 「うまくいかなかったらもう一度実行する」という直感的な操作が安全であるべき
- 自動化（CI等）での使用に耐える

**実現方法：**
- マーカーの再計算は常に現在のコンテンツから導出される（状態の累積ではない）
- ハッシュは正規化された内容から決定的に算出される
- needフラグは現在の状態から再計算可能

### 5. プライバシーへの配慮

AIプロバイダーへのデータ送信は、ユーザーが意図したコマンド実行時のみ発生する。バックグラウンド分析、事前送信、キャッシュ目的の暗黙的通信は行わない。

OpenAI APIを使用する場合、`store: false`をハードコーディングし、プロンプト・応答がサーバーに保存されないことを保証する。

### 6. 構造情報の保持

テキスト正規化（stripMarkdown等）においては、プレーンテキスト化と引き換えに構造情報を失わない。見出しと本文、リスト項目の境界など、文書の構造的分離は改行により明示的に保持される。

**理由：**
LLMへのプロンプト品質を最大化するには、文脈の理解可能性が重要である。構造的に分離されているべき要素が連結されると、LLMは誤った解釈をする。正規化は雑多な記法差異を吸収するためのものであり、構造情報まで破棄すべきではない。

**実現：**
`stripMarkdown`は見出し・リスト・引用ブロック終了時に改行を挿入し、構造境界を保持する。最終正規化でも改行は維持され、LLMが文脈を正しく理解できるテキストを生成する。

## 目指すところ / 目指さないところ

### mdaitが解決する問題空間

- **継続的な多言語文書管理**：原文の変更を追跡し、必要な箇所のみ再翻訳する
- **翻訳運用の可視化**：どのファイルのどのユニットが翻訳待ちか、一目で把握できる
- **用語の一貫性**：用語集を実際の翻訳に確実に反映し、新規用語を自動提案する
- **文脈保持翻訳**：周辺コンテキストと前回訳文を参照し、LLMの品質を最大化する

### mdaitが意図的に対象外とする領域

- **リアルタイムコラボレーション**：mdaitは非同期・ファイルベースのワークフローを前提とする。複数人が同時に同じファイルを編集する衝突解決は、gitに委ねる
- **WYSIWYG編集**：mdaitはMarkdownのテキスト構造を尊重する。リッチテキストエディタは提供しない
- **翻訳品質の完全保証**：LLMの出力は確率的である。mdaitは構造チェックと用語統一で品質を支援するが、最終的な品質判断は人間が行う
- **Markdown以外のフォーマット**：HTML、DOCX、PDFなどの翻訳は対象外。Markdownの構造（見出し、リスト、コードブロック等）を活用することで、差分管理と文脈抽出を実現している

## 中核となる設計原則

### P1: ユニットベースの管理

Markdown文書を「ユニット」単位に分割し、各ユニットを独立した管理単位とする。ユニット境界は見出しレベルで決定され、各ユニットは自己完結したマーカーを持つ。

これにより：
- 部分的な変更を部分的に再翻訳できる
- ファイル内のどこが変わったかを構造的に把握できる
- 翻訳の進捗を粒度細かく追跡できる

### P2: ステートレスな再計算

すべての状態（ハッシュ、need、from）は、現在のファイル内容から再計算可能である。過去の実行履歴に依存しない。

これにより：
- どんな状態からでも`sync`で復帰できる
- マーカーの不整合が発生しても、再実行で修復できる
- 履歴が壊れても翻訳管理は継続できる

### P3: 差分駆動のワークフロー

変更されたユニットのみに`need:translate`が自動付与される。翻訳者は「全体を確認する」のではなく、「needフラグがついたユニットだけを処理する」。

これにより：
- 大規模文書でも翻訳作業量が最小化される
- 変更箇所が明示的に可視化される
- 作業の優先順位が自明になる

### P4: LLMをdiff-aware reviseの主戦力とする

原文が変更された場合、LLMに「原文の差分」と「前回訳文」を提示し、訳文への差分パッチを生成させる。全文再生成ではなく、変更箇所のみを更新する。

これにより：
- 手修正された訳文が最大限保持される
- 変更箇所以外のノイズが発生しない
- LLMの文脈理解力を最大限活用できる

### P5: 層の責務分離とデータフローの明確化

mdaitは以下の層構造を持つ：

```
UI層 → Commands層 → Core層 → Utils層
              ↓
           API層
Tools層 ─────→ Commands層 / Core層
  ↑
GitHub Copilot
```

- **UI層**：VS Code統合、ユーザーとのインタラクション
- **Commands層**：ビジネスロジック、ワークフロー制御
- **Core層**：純粋な翻訳ドメインロジック（ユニット分割、ハッシュ計算、差分検出）
- **API層**：外部AI サービスとの通信
- **Tools層**：LanguageModelTool API、GitHub Copilot Chatなど外部AIからの機能呼び出し
- **Utils層**：汎用機能、I/O、ログ

各層は明確な責務を持ち、下位層は上位層に依存しない。Core層は純粋関数に近い設計とし、テストとメンテナンスを容易にする。Tools層はCommands層やCore層の既存機能を薄くラップし、新しいビジネスロジックは持たない。

### P6: VS Code標準パターンへの準拠

mdaitは、VS Codeエコシステムの一部として設計される。独自UIは最小限に抑え、VS Code標準のUI要素（TreeView、CodeLens、Hover、Progress等）を活用する。

これにより：
- 他のVS Code拡張と一貫したUXを提供できる
- VS Codeの進化に追従しやすい
- ユーザーの学習コストが低い

## アーキテクチャの全体像

### 層構造の設計意図

#### Core層：翻訳ドメインの心臓部

- Markdownをユニットに分割する（`MarkdownItParser`）
- ハッシュを計算し、内容を正規化する（`Normalizer`, `HashCalculator`）
- ソースとターゲットのユニット対応を検出する（`SectionMatcher`）
- ステータスを集約する（`StatusManager`, `StatusCollector`）

Core層はVS Code APIに依存せず、純粋なTypeScriptで実装される。これにより、ロジックの単体テストが容易になり、将来的な他環境への移植可能性も担保される。

#### Commands層：ワークフローの指揮者

- `sync`：ユニット同期、差分検出、needフラグ付与
- `trans`：翻訳実行、用語集連携、品質チェック
- `term`：用語検出、用語展開
- `translate-selection`：マーカーレスのオンデマンド翻訳

Commands層は、Core層の純粋関数を組み合わせて、実際のユーザーワークフローを実現する。進捗表示、エラーハンドリング、キャンセル対応もこの層の責務である。

#### API層：外部世界との橋渡し

- AIプロバイダーの抽象化（`AIService`インターフェース）
- プロバイダーの動的選択（`AIServiceBuilder`）
- レート制限、リトライ、タイムアウトの制御

API層は、LLMの多様性を吸収する。OpenAI、Ollama、VS Code LM APIなど、異なるプロバイダーに対して統一されたインターフェースを提供し、Commands層はプロバイダーの違いを意識しない。

#### UI層：VS Codeとの融合

- StatusTreeProvider：翻訳状態のツリー表示
- CodeLensProvider：マーカー行へのインラインアクション
- HoverProvider：翻訳サマリの表示
- Welcome View：初期設定ガイド

UI層は、mdaitの内部状態をVS Codeの標準UIパターンで可視化する。独自のWebビューは使わず、VS Codeネイティブな体験を提供する。

#### Tools層：外部AIからのアクセス

- LanguageModelTool API：GitHub Copilot ChatなどからのTool呼び出し
- Get Status Tool (`mdait_getStatus`)：翻訳ステータス取得
- Sync Tool (`mdait_sync`)：翻訳マーカー同期
- Translate Tool (`mdait_translate`)：ファイル翻訳

Tools層は、Commands層やCore層の既存機能を薄くラップし、LanguageModelToolResultとして返す。新しいビジネスロジックは持たず、VS Code LM APIに準拠した確認UIを提供する。

## 将来の拡張に対する姿勢

### 拡張可能にするもの

- **AIプロバイダー**：新しいLLMプロバイダーを`AIService`実装として追加できる
- **出力戦略**：翻訳結果の出力先（クリップボード、新規タブ等）を`OutputStrategy`として拡張できる
- **用語集フォーマット**：CSVから他のフォーマット（JSON、YAML等）への移行が可能
- **プロンプトカスタマイズ**：すべてのシステムプロンプトを外部ファイルで上書きできる
- **横断的知識の蓄積**：翻訳メモリ（TM）のように、ユニット横断の知識は`.mdait/`配下に独立ファイルとして管理する。文書内マーカーに含めるのは「そのユニット固有の状態」のみとし、横断的データは外部ストアに委譲する。TMは純粋なテキストベースで管理し、Markdown記法は除去する。短文・数値のみなど翻訳価値のない断片はフィルタリングし、品質の高い翻訳参照のみを蓄積する

### 固定するもの

- **マーカーフォーマット**：`<!-- mdait hash from:xxx need:yyy -->`形式は、互換性のため固定される
- **ハッシュアルゴリズム**：CRC32は、既存マーカーとの互換性のため変更しない（拡張時は別フィールド追加）
- **Markdownパーサー**：markdown-itを基盤とし、プラグインで拡張する
- **ユニット境界**：見出しレベルベースの分割原則は維持する（ただし、手動マーカー追加で細分化は可能）

### 意図的な制約

- **並列実行**：現在は順次実行を採用している。これはキャンセル即応性とAI APIレート制限対策を優先した結果である。将来的に並列数制限（セマフォ方式）を導入する可能性はあるが、無制限な並列実行は採用しない
- **マーカー最小主義**：マーカーに含める情報は最小限に抑える。冗長な情報をマーカーに埋め込むと、可読性が損なわれ、将来の拡張が困難になる
- **ファイルパス管理の一元化**：ファイルパス（用語集、TM等）の取得ロジックは`Configuration`クラスに集約し、コマンド層では直接パス構築を行わない。これにより、将来的な設定のカスタマイズ（パスの変更、複数ファイル対応等）が容易になり、コード重複が回避される
